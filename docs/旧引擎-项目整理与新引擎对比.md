# 旧引擎（生产）项目整理 · 与不稳定的新引擎（fusion/KVMem）对比

> 口径：x99（Ubuntu 22.04 + RTX 3080 20GB 单卡 sm_86），模型 Qwen3.8-27B GSQ-RCO IQ3_S，
> 引擎日志与监控面板自报数为准。整理日期 2026-10-10。

---

## 一、旧引擎项目整理（**当前生产**）

### 1.1 它是什么

| 项 | 内容 |
|---|---|
| 引擎出处 | `iamwavecut/ninfer-all` @ **60f18c3**（原生 **sm_86** 分支；带 `gguf_blocks_v1` 张量布局，IQ3_S 必需）—— 厂商 `README.txt` 指名 |
| 制品 | `…bundle/bin/ninfer-serve`（厂商原件 1,249,869,248 B）+ ldd 闭包（原生 glibc loader，**不要 Docker、不要 Python 环境**）|
| 模型 | `/data/nvme/ninfer-models/…ninfer`（IQ3_S 3.5 bpw，14 GiB 级，含 Vision + MTP）|
| 服务 | `systemd` 单元 `ninfer.service` + `/data/ninfer/run.sh`；GPU0 独占；实例端口 **18082** |
| 配套 | `ninfer-watchdog.service`（防抢卡）+ `ninfer-monitor`（面板 **18083**，`monitor/`）+ 桌面面板 `双引擎实时吞吐.bat` |

### 1.2 生产参数要点（`/data/ninfer/run.sh`）

- 上下文 **262144（256K）**，KV 量化 `rk4v4` 级；投机 `--spec mtp`（草稿 3）
- **并发 1 执行 + 16 排队**（`--max-concurrency 1 --max-pending-requests 16`）—— 实测 4 并发全部 200，但 `queue` 依次 0.8→1.4→2.1 s（串行服务）；第 18 条起 `429 server_overloaded`
- 检查点/续段：`--device-state-slots 8 --host-state-slots 2`
- 视觉：`--vision`（视觉塔按需借显存）
- **输出上限必须 ≤ 池**：`--default-max-tokens` 压到 **16384**（否则客户端大 `max_tokens` ⇒ worker 崩 + 全 503，而 `/v1/models` 仍 200 假健康）
- 自愈：`NINFER_EXIT_ON_WORKER_CRASH=1`（worker 崩即退出，交给 systemd 拉起）
- 面板口径：`--log-stats-interval-ms 1000`（**每秒**一条 `throughput` 行 ⇒ 面板 `tg` 逐秒刷新、`tg_3s` 滞后分家）

### 1.3 磁盘层（**重启不丢上下文**，已修）

- 参数：`--disk-kv-path /data/nvme/ninfer-disktier --disk-kv-gib 64 --disk-kv-restore`
- 原生行为：只落 **被挤出/已编目** 的续段 ⇒ **单会话从不被挤出 ⇒ 从不落盘** ✗
- **我们的补丁**（`commit-spill`，自编件已上卡）：`commit.cpp` 在请求提交成功、KV 仍绑、且 `unbind_sequence_kv(state)` **之前** `spill_released_owner(state)` ⇒ 增量落盘
- **判据**：单会话跑完 → 直接 `systemctl restart ninfer` → 回同一题面 = **1.2 s**（冷 28.0 s）；被挤出的会话 0.6 s
- 第二层：`--max-private-continuations 1`（出现过第二个会话即挤出落盘）
- 磁盘占用：**稀疏预分配**（名义 64 G；`du` 才是真占用，实测 ~13 G 起随会话增长，超预算 LRU 淘汰）

### 1.4 运维与回退

- 重启代价：**9–19 秒**（重启后会话由磁盘层恢复，不再是 27 s 全量重算）
- 回退：`cp /data/ninfer/bundle/bin/ninfer-serve.bak-*-diag /data/ninfer/bundle/bin/ninfer-serve && systemctl restart ninfer`
- 自编重建：`scripts/diag-spill-pipeline.sh`（改 `.cpp` **增量编 ~3 分钟**；改 cmake 文件才全量 ~36 分钟）；产物在镜像 `/usr/local/bin/ninfer-serve`
- ⚠ 现跑的是**自编补丁件**，与厂商原件不再逐字节一致 ⇒ 以后更新必须从这棵树重编

### 1.5 已知遗留（旧引擎自身）

- `max_tokens ≫ 池` 会崩 worker（**引擎侧未修**，靠把默认值压到 16384 规避）—— 新版文档里这条是 §1.2 同源问题
- 并发只能排队（1 执行），高并发靠队列与 429 兜底
- 上下文上限受「池 = 逻辑上下文」约束：256K 是这个显存量级的现实档

## 二、新引擎（fusion / KVMem 环）整理

### 2.1 它是什么

| 项 | 内容 |
|---|---|
| 出身 | **下游衍生**：上游 NInfer-all + 移植 `tancau/ninfer-kvmem-ring` + `kvmem-qw3`（Di Chai）8 件；新增 44 件、改动 92 件（逐文件 SHA256 对账）|
| 核心能力 | **让「设备池 < 逻辑上下文」成立**：内容打分选页 → 降级到主机 KV → 按需搬回 → 隐藏页装掩码 ⇒ 20 GB 卡跑 **512K / 1M** 上下文 |
| 实例 | 端口 **18084**；我们实测过 **384K 档**（CTX 393216 / POOL 158720 / HOSTKV 5120 / DSS 10）与 **512K 档**（CTX 524288 / HOSTKV 8192 / DSS 10 / GPU0 96.4%）|

### 2.2 性能（我们实测）

| 项 | 旧引擎 | 新引擎 |
|---|---|---|
| 长任务 decode | 114.2 tok/s | **213.9 tok/s（+87%）** |
| 512K 环档 | 不支持（256K 封顶）| 支持；400K 题面全量 prefill 13m01.6s |
| 环 vs 非环代价 | — | prefill 1.23k → 1.06–1.13k tok/s（窗口 8/16/32K 影响 ≤2–4%，**代价主要在"环"**）|
| 1M 档尝试 | — | 缓存 2,918 槽 / 命中 37.7% / decode 21–31 tok/s = **−45%** ⇒ 判不划算，已回切 512K |

### 2.3 稳定性：**"bug 太多"的具体账**

新引擎自带 `docs/06-Bug手册.md`，**未解决项就有 5 类**：

| 编号 | 问题 | 级别 |
|---|---|---|
| §1.1 | **超窗口"正中针"静默丢失** | **唯一正确性级**：答错不报错 |
| §1.2 | worker 崩且不自愈（全 503），而 `/v1/models` 仍 200 | 假健康 |
| §1.3 | 12 GB 卡跑官方快档差 105 MB 就 FATAL | 起不来 |
| §1.4 | 自检脚本"假红"（12 GB 卡可能被判 FAIL）| 误判 |
| §1.5 | `SHA256SUMS.txt` 会被误读为"禁止修改" | 误判 |

另有整册口径陷阱（§3）、红线（§4）、"暂时不打算做"（§5）。我们**自己撞到并定位**的崩溃族（全在环/预留/检查点链）：

| 签名 | 位置 |
|---|---|
| `active KV snapshot page ownership is not ordered` | `kv_store.h:1513` |
| `Paged KV single-page materialization exceeds reservation` | `paged_kv_cache.cpp:528` |
| `KV activation reservation is stale` | `kv_store.h:1049` |
| `KV activation capacity reservation changed` | `kv_store.h:1107` |

**我们做的三层防护**（缺一不可）：① 补丁 P1/P1b/P3（把抛异常的清理路径改成 `noexcept` 诊断、容量不足归到 `ContextCacheExhausted`）；② 引擎 `--recover-invariant-failures`（失败请求、保住队列，不再整体僵尸）；③ `NINFER_EXIT_ON_WORKER_CRASH=1` + systemd 自动拉起。此基础上回归全绿：`verify-512k2` 四段无 ISSUES、`stress-longsession` 30 轮 **FAIL 0/30**、`NRestarts=0`。

### 2.4 运维摩擦

- **环 ⇒ `--max-concurrency` 必须为 1**（`KVMem content scoring requires --max-concurrency 1`）⇒ 并发能力与旧引擎同级（甚至更受限）
- 上下文档位一改就要**五处同步**（systemd drop-in、Hermes 供应商 `context_length`、Web 面板、桌面面板采样器 ctx 口径、渲染器）
- 显存吃紧（96.4%），池容量与 `HOSTKV` 一旦过配就触发主机内存地板（实测 `available` 曾掉到 56 MB，须回退 HOSTKV 10240→8192）
- 崩溃后**假健康**：`/v1/models` 仍 200，必须看 `NRestarts` 与日志

## 三、结论：为什么生产用旧引擎

| 维度 | 旧引擎（+我们的补丁）| 新引擎（fusion/KVMem）|
|---|---|---|
| 上下文 | 256K（池 = 逻辑上下文）| **512K/1M**（池可小于上下文）|
| 长任务吞吐 | 114.2 tok/s | **213.9（+87%）** |
| 重启不丢上下文 | **1.2 s（已补）** | 同机制（其 `flush_disk_tier` 与旧件同源，**我们的 `commit-spill` 修复同样适用**）|
| 契约（并发/参数）| 简单、稳定；并发 1+16 排队 | 环**强制**并发 1；档位改动要多处同步 |
| 崩溃族 | 无环相关崩溃 | **环/预留/检查点链 4 个签名** + 自带 5 类未解决（含 1 个正确性级）|
| 维护成本 | 低（一次补丁 + 一键流水线）| 高（三层防护、每月跟上游、每次改档要同步五处）|
| 结论 | **生产选择**：稳定优先，长上下文需求用 256K 档满足 | 适合作**实验/长上下文专用档**，不建议无防护上生产 |

**一句话**：新引擎换来的是「小显存跑超长上下文 + 更高的长任务吞吐」，代价是「正确性级未解决项 + 环特化崩溃族 + 每次调档的多处同步」；旧引擎把「重启不丢上下文」补齐后，在 256K 这个生产档位上已经**又快又稳**，所以生产留在旧引擎。
