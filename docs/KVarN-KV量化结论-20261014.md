# KV 量化：本轮结论与现状（2026-10-14）

> 结论一句话：**这套 KVarN（Hadamard 旋转 + 双向 Sinkhorn 方差归一）在本机这个模型上打平生产 `rk4v4`，省不了字节，也不比 llama.cpp 原生 KV 档更值；这条线冻结，等后人。**
> 下面每条都附实测数字与出处；没跑出来的没写。

## 1. 起点：KVarN 论文/vLLM 分支宣称什么

- 论文：arXiv **2606.03458**《KVarN: Variance-Normalized KV-Cache Quantization Mitigates Error Accumulation in Reasoning Tasks》；vLLM 实现 `huawei-csl/KVarN`（原生 attention 后端，`--kv-cache-dtype` 一个开关，宣传"3-5× 上下文、吞吐高于 FP16、FP16 级精度"）。
- 宣称：**2.3 bit/元素近无损**、量化开销 **0.18%**；机制 = Hadamard 旋转 + 对 K/V 两个轴做双尺度方差归一（Sinkhorn），主打**解码期误差累积**（并提出 `pseudo-decode` 评测口径）。
- **必须注意的口径**：它的 2.3 bit 是**三段式布局的平均值** —— sink token 与最近若干 token **保持 FP16**，只有中间 body 走 2bit；即"2bit"不是全序列 2bit。

## 2. 我们在真实 KV 上的实测（口径先立住）

三档独立校验：旋转与上游 `kvarn_wht_128` **逐位相同（3,145,728 元素 0 差）**；量化 kernel 在 `iters=0` 下 **576/576 record 逐字节一致**；`iters=8/16` 与 llama CPU 口径在真实 tile 上 cos 一致（只差末位）。⇒ **换实现不会有变化，只有改算法/位宽分配才可能有变化。**

离线 oracle（同一条管线，真实 pre-RoPE tile，语料 A/B/C 三段互不重叠，锚点复现误差 0）：

| 位宽档 | 相对生产 `rk4v4` 的 ΔPPL | 结论 |
|---|---|---|
| K4V4（=上游默认 4bit） | −0.089% / +0.224% / −0.025% | 打平（跨语料摆幅 0.31%，判据只有 0.10% ⇒ 这套评测在 0.1% 档分辨力不足） |
| **K4V2**（论文主打的 2bit 侧） | **+2.551% / +2.907%** | **判死**（在这个模型上 2bit V 一切改法最好也只到 +1.68%） |
| K4V3 | +0.255% / +0.587% | 不过线；改尺度求解（加权 LS/分位裁剪/refine）最好 +0.1189%，仍不过 |

**与论文/社区常识相反的一点**：KIVI/KVTuner 一类工作都报告"**K 侧敏感、V 侧宽容**"，而在本模型（Qwen3.8-27B 这个制品）上实测正好反过来 —— **K 侧 4bit 近乎免费**（K4only −0.179%/+0.006%，K 逐向量 cos 0.997055 > 生产 rotated Lloyd-4 的 0.995566），**V 侧才是瓶颈**（V2only +2.269%/+2.499%）。这也解释了为什么"2bit V"路线在这里走不通。

## 3. 引擎侧移植实测（`ninfer`，同语料同工具）

| KV 档 | 语料 A PPL | 语料 B PPL | vs 生产 `rk4v4` |
|---|---:|---:|---:|
| `bf16` | 5.829839 | 6.588490 | −0.3434% / −0.3350% |
| `int8`（K/V 全 8bit） | 5.831034 | 6.595432 | −0.3230% / −0.2300% |
| **`rk4v4`（生产）** | 5.849927 | 6.610634 | 基准 |
| `kvarn128`(K4V4) | 5.848024 | 6.609538 | **−0.0325% / −0.0166%** |

- 质量：**打平生产**（略优一点点），仍逊真 int8 约 0.21%~0.29%，与 `bf16` 差 0.31%~0.32% ⇒ **"K4V2 达到 FP16"那种预期在这里不成立**。
- 字节：**算法本身 280 = 280（紧凑 record 口径）**——`32·(Kb+Vb)+24` ⇒ K4V4 = 140/140；生产 `rk4v4` = 136/144。
  **但本实现落地的 P1 页自足布局是 292 B/token·head**（K 码流 128 + scale 20、V 码流 128 + scale 16；`kvarn_layout.h:61-82`，
  scale leading 的单位是每 token 每 head 的 **FP16 元素数** K=10 / V=8，两条 `static_assert` 钉死）⇒ 比紧凑多 12 B
  ⇒ **上线的真实显存代价是 +4.29%，不是零**。两臂容量行独立证实：`rk4v4` 每 65,536 token +1.1515 GiB
  （65,536 的 2.58 GiB 与生产 317,440 的 7.02 GiB 差分）、`kvarn128` 每 65,536 token **+1.21 GiB**
  （65,536→131,072 的 2.63→3.84，131,072→262,144 的 3.84→6.26 同斜率）⇒ **+4.3%~5.1%**。
- 显存：移植初版按整池容量开 bf16 解码窗口，**倒亏 4.43 GiB**、窗口封顶塌到 65,536；改成"虚拟预留 + 惰性物理后备"后与生产只差 **0.05 GiB**、**262,144 能起**（引擎 tag `window-lazy-physical-20261014`）。
- 吞吐（仍未解决的一笔）：同窗口下 **32K TTFT +39%、prefill 吞吐 −28%**。
- 唯一可能真省字节的变体：**V 侧"通道为行 3bit + 逐 tile 把最能量的 32 个通道提到 4bit"= 252 B**，三语料同号 +0.1224/+0.0564/+0.1046（合并 11,392 token 精确重算 **+0.0837%**）⇒ 含义是"省 10% KV 字节（≈590 MiB，可把窗口从 317440 抬到约 349K）换 +0.08% 量级劣化，再加 30% 级 prefill 变慢"。**按性能优先的取向默认不划算，故不投。**

## 4. 与 llama.cpp 原生 KV 档同数据对拍（重建保真，非 PPL）

- llama 的 KV 允许集合（`src/common/arg.cpp:341-357`）里没有 `q4_K`（权重档，`ggml_row_size(Q4_K,128)` 会 assert），有 `IQ4_NL`。
- 同字节 4.5 bpw（真实 tile，256-dim head 口径，cos_glob）：**K 侧 KVarN 0.9980816 > `llama+rot iq4_nl` 0.9969349 > `llama iq4_nl` 0.9960991 > `llama q4_0` 0.9945548**；**V 侧 `llama iq4_nl` 0.9961466 > KVarN 0.9948257**。
- 增益来源拆解（真实数据 4bit）：K 侧靠**方差平衡** +0.00039、**旋转几乎为零** +0.00004；V 侧靠旋转 +0.00295、**平衡是净负项** −0.00250。杠杆大小：`q4_K 的 per-32 min+6bit 子 scale` > `Hadamard 旋转` > `iq4_nl 非线性码本` > `KVarN 的 Sinkhorn 平衡`。
- 这些差都在千分位，而我们实测证明**逐向量 cosine 不是 PPL 的有效代理量**（某变体 Vcos 0.9875 ≪ K4V4 的 0.9952，语料 A 的 PPL 却与后者小数点后四位相同）⇒ 只能说"码流层面各法都在千分位互相咬"，判不出质量优劣。PPL 层要比 llama 原生档，得另建 llama.cpp 运行面，未做。

## 5. 现状

- **生产 = 旧生产01**：仍是厂商原件 `ninfer-serve` md5 `2cbd88ab06318c81b695ec64c72b433d`、`--kv-dtype rk4v4`、`--max-context/--kv-capacity 317440`；本轮**一个字节都没换过**。快照（含引擎件副本、模型 md5、单元与标定件、RESTORE 步骤）在 x99 `/data/kvarn/backup-prod01-20261014/`。
- 服务当前是 **stop + disable** 状态（`ninfer`、`ninfer-watchdog`），面板 `ninfer-monitor` 在跑；是否交还没由人拍。
- KVarN 的移植件与全部取证都在盘上（引擎 tag `window-lazy-physical-20261014`；oracle/消融/对拍的原始数据 ~700 份），没删任何东西。

## 6. 给后人的四条起点

1. 先修引擎级 ngram bug（`--ngram-draft-tokens 0` 触发 FATAL；混合起草写入的 KV ≠ 冷算 KV ⇒ 门禁 `ctrl/rst/rst2` 过不了）——这条**与 KVarN 无关**，任何新件上生产都得先过。
2. 要把 0.1% 级的质量差判准，评测集得从现在的 11,392 token 涨到 **5 万 token 以上**（现在同臂跨语料漂移 0.07%~0.34%）。
3. `K4Vprom_k32` 若要落地需要**新 V 码流**（3bit 主码 + k 个通道 4bit 支码 + 每 tile 256 bit 掩码）与 encode 侧逐 tile 通道能量排序，不是"加个位宽 case"。
4. 本模型的敏感侧与主流论文相反（**V 重 K 轻**）——任何"照论文位宽分配直接移植"的方案在这里都要先过这一关。
