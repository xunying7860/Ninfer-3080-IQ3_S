## 2.1 K4V2_g128 单 tile 逐字节布局（示例档；主档为 K4V4，见 §2.3）

D=256，head_slices=2，K=4bit，V=2bit，128 token：

```
offset  size    内容                    说明
─────────────────────────────────────────────────────────────
     0  16384   K payload   4-bit × (256×128)  = 256×128×4/8
 16384    512   K s_col     fp16 × 256        (make_layout 的 head_dim=256)
 16896    512   K zp        fp16 × 256
 17408    256   K s_row     fp16 × 128
 17664   8192   V payload   2-bit × (128×256) = 128×256×2/8
 25856    512   V s_col     fp16 × 256
 26368    256   V s_row     fp16 × 128
 26624    256   V zp        fp16 × 128
─────────────────────────────────────────────────────────────
 26880 B / 128 token = 210 B/token/KV head    ← ①`make_layout` 口径（非 arena 真值；arena = 216）
```

**注意**：这是 **①`make_layout` 口径——仅测试调用、非分配口径**（D256 会低估）；真实分配见下段 record 口径，每格 = 本表 + 6 B/token。

而 CUDA kernel 侧（`kvarn_quantize_tile`）是按 **128×128 record** 处理的，D256 时**每个 head 有 2 个 slice**。所以实际存储是：

```
tile_bytes(256) = 2 × record_bytes(128) × 2(K,V)
```

其中单个 128×128 record（4-bit）：

```
payload   128×128×4/8 = 8,192 B
scale     fp16 × 128  =   256 B   (best_row[row] × scale[row])
zp        fp16 × 128  =   256 B   (best_row[row] × lo[row])
other     fp16 × 128  =   256 B   (best_col[row]，列因子)
──────────────────────────────
          8,960 B
```

K 两个 slice = 17,920；V（2-bit，payload 4,096）= 2×(4,096+768) = 9,728。合计 **27,648**，与 `make_layout` 的 26,880 差 768 B。

**这个差异已查清**——`make_layout` 用 head_dim=256 摊 scale（每 head 一套 256 维 s_col），而 record 布局是每个 128×128 slice 各一套 128 维。**对齐方式不同**。

**结论**：768 B 差 = 6 B/token，来源是 record 口径把 `other_axis`（列因子）按 slice 各存一份（2×128 项），而 `make_layout` 只存一份。`make_layout` 在引擎里**无调用者**（全仓唯一调用者 `tests/test-kvarn.cpp`，且 head_dim=128）⇒ **容量预算与 kernel 读写都只能用 record 口径**，不得再以 `make_layout` 为预算依据。

## 2.2 通用公式

```c
// make_layout（allocator 口径，head_dim 可为 64/128/256/512）
k_payload = packed_bytes(head_dim * group, key_bits);
k_s_col   = head_dim * 2;
k_zp      = head_dim * 2;
k_s_row   = group * 2;
v_payload = packed_bytes(group * head_dim, value_bits);
v_s_col   = head_dim * 2;
v_s_row   = group * 2;
v_zp      = group * 2;
tile_bytes = align_up(sum, 8);

// packed_bytes
(n_values * bits + 7) / 8;

// make_record_layout（kernel 口径，record_dim ∈ {64,128}）
rows = value ? 128 : record_dim;
cols = value ? record_dim : 128;
payload = packed_bytes(rows * cols, bits);
record_bytes = payload + (2*rows + cols) * 2;
```

## 2.5 staging / tail 开销（要计入总账）

| 项 | 每全注意力层 | 32 层 | 48 层 | 64 层 |
|---|---:|---:|---:|---:|
| stage 2 slot（128 tok × 4 head × 256 dim × K/V × fp16） | 1.0 MiB | 32 MiB | 48 MiB | 64 MiB |
| tail 1024（精确 F16） | 4.0 MiB | 128 MiB | 192 MiB | 256 MiB |

beellama 实测参照（Gemma 4 31B @ 16K，`--kv-memory`）：

| 档 | Persistent KV | Exact history + reserve | Staging | KV-related peak |
|---|---:|---:|---:|---:|
| kvarn5 / 0 | 1170.70 MiB | 110.86 MiB | 220.00 MiB | 1290.02 MiB |
| kvarn5 / 1024 | 1337.58 MiB | **880.86 MiB** | 20.00 MiB | 1463.64 MiB |

**两条教训**：

1. **tail 1024 比 tail 0 多 770 MiB**（880.86 vs 110.86）——tail 不是免费的。
2. **request-0 时 KVarN 可能比 Q4_0 更占内存**（Qwen @64K 实测 **+8.4%**），因为必须保留 intrinsic F16 suffix + staging。beellama 原文：

> Request-zero is an explicit architectural tradeoff rather than a hidden regression: KVarN must retain its intrinsic F16 suffix and compression staging, while Q4_0 request-zero has neither an exact overlay nor tail-merge scratch.

**所以"省 22.9%"是纯 record 字节，净收益要减掉 stage/tail。** 在 20G 卡上这不是小数。
