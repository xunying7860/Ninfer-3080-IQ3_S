## 结论先行

**分开说，因为两个口径的答案不同（都给了数字）：**

| 口径 | 判定 | 数字 |
|---|---|---|
| **① 结构层**（同一蝶形结构 + 单点精确 2^-4） | **PASS（逐位相同）** | 三组共 3,145,728 元素，`max|A'-B|` = **0.000000e+00 / 0.000000e+00 / 0.000000e+00**（gauss / outlier / bound） |
| **② 逐字层**（两侧各自带的归一化常量与施加位置，任务书写死的判据） | **FAIL（1 PASS + 2 FAIL）** | `max|A-B|` = **4.768372e-07**（gauss，PASS）/ **1.220703e-04**（outlier，FAIL）/ **3.814697e-06**（bound，FAIL） |

- ② 的 FAIL **不是结构差**：把 beellama 的蝶形结构配上**单点精确 2^-4** 后与 ninfer 逐字实现 **逐位完全相同**（0 差 × 3,145,728 元素）。差异 100% 来自 beellama 那两个 float 常量（`0.08838834764831845f`、`0.7071067811865475f`，各带 1.711e-08 相对误差，合成 `0.062499997860716139` 与精确 1/16 差 **3.423e-08 = 0.57 ulp**）以及「归一化施加在最后一个蝶形**之前**」这两点。
- **配对层 = 恒等映射**：256 个单位向量探测，非恒等行 **0 / 256**、负号行 **0 / 256**，匹配残差 **3.725290e-09** ⇒ **不需要任何 permutation，也不需要符号翻转**：beellama 的 slice0/slice1 就是逻辑 D256 head 的 dim[0..127] / dim[128..255]，与 ninfer 的自然 dim 序 `index = lane + 32*r` 一一对应。
- **平均 cosine = 1.000000000000000**（三组都是；最小值 0.999999999999997 ~ 0.999999999999999）。
- **oracle 三方对拍**：`oracle/make_tiles.py::rotate_d256`（gate2 输入 tile 的旋法）与 beellama 逐字路径 **bit 全同（0 / 2048 元素不同位）**，与 ninfer 路径 max|Δ| = **2.384186e-07**（同 8 个向量）。

**一句话建议**：**照搬 ninfer 侧**（保留现有 `normalized_hadamard_d256_inplace`，不必在 ninfer 里补跨 slice 蝶形）——因为两侧结构逐位相同、ninfer 侧的归一化是精确的 2^-4，beellama 侧反而多一层 1.7e-08 常量误差 + 多一次跨 slice 蝶形与两次乘；代价：放弃「与 beellama 的 record 逐位互换」这个目标（该目标已由 gate2 判定在跨构建下不可达）。

## 3. 归因：差在哪（常量 vs 结构）

`out/gate.txt:4-7`（常量算数原文）：

```
[const ] beellama 0.08838834764831845f = 0.088388346135616302  1/sqrt(128) = 0.088388347648318433  rel.err = 1.711e-08
[const ] beellama 0.7071067811865475f  = 0.70710676908493042  1/sqrt(2)   = 0.70710678118654746  rel.err = 1.711e-08
[const ] beellama 合成归一化 wf*sf = 0.062499997860716139  vs ninfer 2^-4 = 0.0625  rel.diff = 3.423e-08 (0.57 ulp)
[const ] ninfer 归一化 0x1p-4f = 0.0625（2 的幂，float/double 均精确可表示，无常量误差）
```

**三条独立证据把差异钉死在「常量 + 施加位置」，与蝶形结构无关：**

1. **变体 A'（beellama 的蝶形结构 + 单点精确 2^-4）vs B = 逐位 0 差**：三组 3,145,728 元素 `max|A'-B| = 0.000000e+00`。
   A' 与逐字 A 的唯一区别：`kvarn_wht_128` 里的 `×0.08838834764831845f` 与 `cross_slices` 里的 `×0.7071067811865475f` 都不做，改成最后一次性 `×0x1p-4f`（源码内标 `[GATE1 变体，非逐字]`）。
   ⇒ **蝶形顺序（stride 递增 1→128）、每一级的配对 (i, i+stride)、a=低 / b=高 的符号约定、slice↔dim 与 lane↔dim 的映射，两侧完全一致**；连舍入顺序在把归一化挪到单点后都逐位重合。
2. **double 域复刻两条路径**：三组的相对差都恰好是 **3.423e-08**（= 上面的常量比），而 float 实测「最大绝对差所在元素」的相对差是 **7.9e-08 ~ 1.8e-07**（多出来的部分是「归一化施加位置不同」带来的 float 舍入：beellama 在最后一个蝶形前就把值乘小了，ninfer 是蝶形做完再乘精确 1/16）。
3. **D256/512 的几何本身是「整 head Hadamard」**：上游注释 `llama-kv-cache-kvarn.cpp:130-131`（Version 9）+ oracle `make_tiles.py:53-63` 的 `rotate_d256` 就是「2 片 WHT128 → 2 点蝶形 ×1/√2」，且与 beellama 逐字路径 **bit 全同**。

（顺带：beellama 是**先归一化后做最后一级蝶形**，ninfer 是**全部蝶形后一次精确缩放**——所以 ninfer 侧更准：自逆误差在三组里都更小：9.54e-07→7.15e-07、1.46e-03→6.09e-04、1.53e-05→1.19e-07。）

## 7. 建议：移植照搬哪一侧 + 代价

**照搬 ninfer 侧**（保留 `normalized_hadamard_d256_inplace` 现状，**不要**在 ninfer 里补 `cross_slices` 那道蝶形）。

理由（都是数字）：
- 结构、配对、符号、映射**逐位相同**（A' vs B：0 差 / 3,145,728 元素；映射 0/256 非恒等、0/256 负号、残差 3.73e-09）；
- 两侧唯一差别是归一化的**常量与位置**：beellama = 两个 float 常量相乘（各 1.711e-08 相对误差，合成 0.062499997860716139，与精确 1/16 差 0.57 ulp）且施加在最后一个蝶形**之前**；ninfer = 全部蝶形后一次精确 2^-4。**ninfer 侧更准**（自逆误差更小，见 §5）；
- 这个 3.4e-08 的算子级差比实际量化噪声小 **5 个数量级**（gate2 实测合成数据 `maxd|s_col| = 7.486e-03`、真实数据 `3.338e-06`；`GATE2-量化kernel逐字节对拍-20261013.md:139,150`），在质量上不可测。

代价：
- 照搬 ninfer 侧 ⇒ **放弃「与该 beellama 构建逐位互换 record」**。WHT 这一层就已经有 1.8e-07/per-element 的相对差，跨引擎共享 cache 时会在量化取整边界上偶发翻位（与 gate2 实测的「每档 ~2.7 字节/record 的 ulp 效应」同阶）——而 gate2 已经判定逐位互换在跨构建下不可达（上游用 `-use_fast_math` 时连 `iters=0` 都 371/576 record 有差异，`GATE2…md:226`），所以这条代价本来就不成立。
- 反过来照搬 beellama 侧（在 ninfer 里再补一个跨 slice 蝶形，与 `hadamard_d256.cuh` 并存）⇒ 代价是：多一份 128 维 lane 实现 + 每 256 维多 2 次乘 + 2 次跨 slice 的加/减，**并主动引入** 1.7e-08 的常量误差与「归一化埋在蝶形中间」的舍入（自逆误差从 1.19e-07 恶化到 1.53e-05/bound）。唯一收益是「与 beellama 逐位更像」，而该目标已被 gate2 否掉。

（若主控另有「读 beellama 产的 record」需求，不要靠改 WHT 解决——两侧差是 3.4e-08 的**全局标量**×各元素舍入，按 gate2 的结论，正确做法是用设备侧 + `-use_fast_math` + 同迭代数逐位复刻量化，而不是动旋转。）
