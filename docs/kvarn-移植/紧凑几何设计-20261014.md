## 1. 前提与口径更正

### 1.1 本文件使用的口径（不再自造）

- **紧凑 record 口径**（= 上游 `llama_kvarn_make_record_layout` 的实际分配口径，`ref-beellama/src/src/llama-kvarn.cpp:673-688`）：
  `record_bytes = rows*cols*bits/8 + (2*rows + cols)*2`，`rows=cols=128`；D256 ⇒ `head_slices=2`（`llama-kvarn.cpp:690-698`，256 → `{128, 256, 2}`），一个 tile = 2 slice × (K record + V record)。
  ⇒ 每 token 每 head = `32·(Kb+Vb)+24`。
- **ninfer P1 页自足口径**（= 当前引擎实际分配，`kvarn_layout.h:78-85`）：`32·(Kb+Vb)+36`。
- **生产 `rk4v4`**（`RotatedLloyd4KeyInt4Value`）：`paged_kv_storage.h:83-93` ⇒ key 128+4×2=136、value 128+8×2=144 ⇒ **280 B/token/KV head**。
- **leading 规则**（`kvarn_layout.h:62` + `paged_kv_storage.h:119-129`）：`k_code=32·Kb`、`v_code=32·Vb`、`k_scale=10`、`v_scale=8`（单位 = 元素；码 plane U8，scale plane FP16）。
- **页粒度**：`kPagedKVPageSize = 64`（`src/core/paged_kv_cache.h:19`），1 tile = 2 页（`kvarn_layout.h:36 kKvarnPagesPerTile=2`）。

## 2. 布局图与偏移表

### 2.1 紧凑 record 口径（D256，每 KV head）

```
tile (128 token, 1 KV head) = 2 slice × ( K record + V record )
   slice s ∈ {0,1}  覆盖全局维 d = 128·s + r,  r ∈ [0,128)

K record(8960 B @4bit, dim-major)          V record(8960 B @4bit, token-major)
┌──────────────────────────────┐            ┌──────────────────────────────┐
│ 0     .. 8191   payload      │            │ 0     .. 8191   payload      │
│   row = dim r (128), col = t │            │   row = token t (128),       │
│   (128 token 的扁平位流)      │            │   col = dim r (128)          │
├──────────────────────────────┤            ├──────────────────────────────┤
│ 8192  .. 8447   scale_axis   │ fp16×128   │ 8192  .. 8447   scale_axis   │ fp16×128 (每 token)
│ 8448  .. 8703   zp_axis      │ fp16×128   │ 8448  .. 8703   zp_axis      │ fp16×128 (每 token)
│ 8704  .. 8959   other_axis   │ fp16×128   │ 8704  .. 8959   other_axis   │ fp16×128 (每维)
└──────────────────────────────┘            └──────────────────────────────┘
           8,960 B × 2 slice × 2 (K,V) = 35,840 B / 128 token = 280 B/token
```

- 上游读侧同一份口径：`ref-beellama/src/ggml/src/ggml-cuda/kvarn.cu:2828-2849 kvarn_materialize_record_value`（`scale_axis = record + payload_bytes`、`zp_axis = scale_axis + rows`、`other_axis = zp_axis + rows`，末式 `(q*scale + zp) * other`）。
- 上游写侧：`kvarn.cu:750-755`（写 `scale_axis[row]/zp_axis[row]/other_axis[row]`）；`kvarn.cu:779-786` 定死"K 转置、V 不转置"（`token = value ? row : col; dim = value ? col : row`）。
- **一条 record 是一个 128-token 的整体**：三个轴都是 tile 级量，不能按页切开。

### 2.2 P1 页自足口径（D256，4 个 plane × 2 页）

```
plane 形状 = { leading, 64, kv_heads, pages }   (paged_kv_cache.cpp:103-107)
页内寻址 = Leading*64*(head + Heads*physical_page) + Leading*page_offset + leading
           (paged_kv_address.cuh:47-61 = kvarn_layout.h:90-97，两者有 static_assert 钉住)

K code   plane  leading 128 B/token   页内 [token 0..63][byte 0..127]（256 维连续）
V code   plane  leading 128 B/token   同上
K scale  plane  leading 10 half/token 列 0..3 scale_axis(维) 4..7 zp_axis(维) 8..9 other(本页 token)
V scale  plane  leading  8 half/token 列 0..3 other(维)      4..5 scale_axis(本页 token) 6..7 zp(同)
```

槽位语义逐列对照见 `P1几何与偏移表-20261013.md` 第 3.2 / 3.3 节（本文 §2.3 与其逐格一致）。

**两条可由本表直接读出的硬事实**：

1. **码流与 token 轴逐字节相同**——P1 相对紧凑多出的字节**全部**是"维轴被复制到第二页"，没有任何编码差异；
2. **维轴在 P1 里两份的值逐位相同**（`kvarn128_write_scale_plane` 对两页用同一份 `sa/zp/oa`，`kvarn128_codec.cuh:284-304` 的 `tt` 只影响 token 轴取值，维轴取值只依赖 `p`）⇒ 去重复**在数值上是恒等变换**，不是近似。

### 2.4 12 B/token 冗余的唯一来源

```
每 tile（128 token，D256）：
  K 维轴 = 2 slice × 128 dim × 2(scale,zp) = 512 half  → 紧凑存 512、P1 存 1024  差 +512 half = +1024 B
  V 维轴 = 2 slice × 128 dim × 1(other)    = 256 half  → 紧凑存 256、P1 存  512  差 +256 half =  +512 B
  K token 轴(other)   = 2 slice × 128 = 256 half  → 两边相同                      差 0
  V token 轴(scale+zp)= 2 slice × 128 × 2 = 512 half → 两边相同                    差 0
  ───────────────────────────────────────────────────────────────────────────────
  合计多花 768 half/tile = 1536 B/tile = 12 B/token  ✔ 与 kvarn_layout.h:17-20 自述一致
```

| 档 | 紧凑 B/token | P1 B/token | 紧凑 tile B | P1 tile B | P1 多花 B/tile | 紧凑 vs 280 | P1 vs 280 | 紧凑 MiB | P1 MiB |

| **K4V4** | **280** | **292** | 35840 | 37376 | 1536 | **±0** | **+12（+4.29%）** | **350.0** | **365.0** |

| **K4V2** | **216** | **228** | 27648 | 29184 | 1536 | **−64（−22.86%）** | −52（−18.57%） | **270.0** | 285.0 |

### 2.6 "每页 64 token、1 tile = 2 页"约束下的对齐与填充代价

| 项 | 紧凑 record | P1 页自足 | 结论 |
|---|---|---|---|
| plane 对齐要求 | 不适用（无 plane） | `alignment = 256`（`paged_kv_cache.h:53`，传入 `paged_kv_cache.cpp:107`） | — |
| 每页/每条字节是否 256 的倍数 | record 8960 = **35×256** ✔；V3 6912 = 27×256 ✔；V2 4864 = 19×256 ✔ | K code 8192 ✔ / K scale 1280 ✔ / V code 8192·V3 6144·V2 4096 ✔ / V scale 1024 ✔ | **两边都没有填充浪费**（逐页/逐 record 整除 256） |
| 行内对齐 | record 内 `other_axis` 起点 8704 = 34×256 ✔ | K scale 行宽 10 half = **20 B，非 16 B 倍数** ⇒ 行起点每 4 行才 16 B 对齐（`P1几何与偏移表-20261013.md` 第 8 节第 2 条已点明） | 紧凑更整齐；P1 的 20 B 行宽只影响 load 效率 |
| 页/tile 计数 | 一条 record 覆盖 128 token = 2 页 | 1 tile = 2 逻辑页（`kvarn_layout.h:36`、`:145-147`） | 两边都要求**池页数为偶数** |
| **容量取整（当前未强制）** | — | `page_count(capacity) = 1 + (capacity−1)/64`（`decoder_state.cpp:13-16`）；capacity = 129/192 ⇒ 3 页（奇数）⇒ 第 2 个 tile 的 `bt[2t+1]` **越界**，而 `kvarn128_encode_kernel:139-141` 与 `kvarn128_window_kernel:172-174` 都无边界检查 | **硬约束**：capacity 必须取整到 128 的倍数（现有检查只覆盖 `--prefill-chunk`，`serve_options.cpp:1662`、`startup.cpp:975`） |

## 4. 风险与硬约束（逐条给判据）

### 4.1 跨页 vs 页自足对 decode 器件（0 smem）的影响

- **判据 1（现状）**：KVarN 的两个解码器件都以 **0 动态 smem** 启动 —— `kvarn128_decode_kernel` `<<<1, kThreads, 0, stream>>>`（`kvarn128_launch.cu:858`、`:863`）、`kvarn128_window_kernel` `<<<grid, kThreads, 0, stream>>>`（`:833`、`:842`）。它们不靠 smem 缓存页，全部直接打全局。
- **判据 2（跨页读本身可做）**：两个核**已经同时持有 page0 与 page1**（`kvarn128_window_kernel:172-174`、`kvarn128_decode_kernel:250-252`，均来自 `bt[2*tile]` / `bt[2*tile+1]`）⇒ "页 1 的读者去读页 0 的维轴"在器件层面只是**多一次全局 load**，不额外占 smem、不需要新寄存器。
- **判据 3（真正卡住的是公共寻址式）**：`paged_kv_element_offset<Leading, Heads>(block_table, head, position, leading)`（`paged_kv_address.cuh:63-69`）**只用 `block_table[position>>6]`**，没有 sibling 项。而 `P1几何与偏移表-20261013.md` 第 7 节已实测"消费核不需要 sibling 页"（`[sib ]` 128 位置 0 失配）——**那是在 P1 下**。改成跨页后，凡是用这条公共式寻址的核都拿不到维轴。
- **⇒ 方案 B 的二选一**：(i) 改公共寻址式（影响面 = 全引擎所有 KV 核，`paged_kv_address.cuh` 被 `prompt_bf16/fp8/i8/k8v4/nvfp4/fast`、`small_t_*`、`k8v4_kernel`、`nvfp4_kernel`、`kernel.cuh`、`sinkhorn_g64_codec` 等十余处 include）；(ii) **另立一条 sibling 通道**：在 host 侧发布 block table 时（`paged_kv_cache.cpp:1122-1137 publish`）**同时**发布一张"tile → 偶数物理页"的表，消费核只读这张表。后者的代价是**新表必须在 capture 前预分配**（见 4.2）。
- **判据 4（真正的语义损失）**：P1 的"任意一页可独立解码"是 `kvarn_layout.h:18-20` 明确写下的设计取舍。去掉它以后，**单独一页不再是完整数据单元**；当前没有任何下游在依赖这条（prefix append 已对 KVarN 全系拒绝，`launch.cu:414-423`），但它是"页级驱逐/页级镜像/部分页读"的前置条件 ⇒ 一旦将来开这些能力，跨页几何要重做。

### 4.2 CUDA graph capture 期禁止 malloc

- **判据（代码即判据）**：`ensure_stage_for` 在分配前显式查 capture 状态并**拒绝**（`kvarn128_launch.cu:295-299`，返回错误串"KVarN staging 必须在 CUDA Graph capture 之前完成分配（warmup 里第一次 append 就会触发）"）；`kvarn128_window` 同样拒绝（`:378-385`）。调用方收到即抛（`:794-798`、`:811-815`）。
- **对新几何的约束**：任何新增缓冲（sibling 页表、维轴独立 plane 的窗口、按 verify columns 的窗口）**必须**复用"第一次 append 时按层分配"这一模式（键 = 量化 K 平面基址，`:283-318`），否则会在 warmup 之后的 capture 期触发 malloc 而被拒。
- **实测证据**：窗口改大后 `131072` 起的启动失败原文是 `text/layers/35 verify columns=4: kv_cache_append: KVarN128 consumer window unavailable`（`kvarn128-验收-20261014.md:64`）——正是这条约束在 capture 期生效的表现。

### 4.3 `metadata.block_table()` 是 device 指针、host 侧不可解引用

- **判据**：`PagedKVBatchMetadata::block_table()` 是 `__device__`-only 且要读 `table_rows[0]`（设备地址）（`paged_kv_address.cuh:37-39`）；`PagedKVDirectMetadata::block_table()` 只是返回 `table`（`:19`），但 `table` 本身也是设备地址。`KvarnTile128BlockTable::resolve()` 故意只给 `__device__`（`kvarn128_launch.h:31-35`），host 误用直接编译错。
- **实机取证**（`kvarn128_launch.cu:6-11` 记录）：`positions[0]` 的 host 读直接 SIGSEGV，故障指令 `mov (%rax),%r12d`，调用链 `kv_cache_append_batch_launch ← causal_attention_prompt_launch ← causal_softmax_attention ← qwen3_5 TextContext::attn_mix ← target_verify_batch ← ProgramImpl::prepare_graphs`。
- **对新几何的约束**：任何"tile → 页"的推导（含方案 B 的 sibling 页）**只能在 device 上做**。host 侧能用的只有：`tokens/128 + 2` 这种上界（`:819-820`）与"D2H 拷回来再解引用"（dump 路径的做法，`:540-543`、`:577-581`）。**不允许**为了算 sibling 而在 host 读 block table。

### 4.4 未满页 / 未封口 tile 的 scale 语义（页级因子要整页才成立）

- **判据 1（量化单元 = 128 token，不是 64）**：三轴全部由 `kvarn128_quantize_tile`（`kvarn128_codec.cuh:133-221`）在**整块 128×128 tile**上算出（`kvarn_std_col` / `kvarn_std_row` 的循环上界都是 `kKvarnSliceDim=128`，`:104-127`）；K 的 scale/zp 按 **dim**（rows=dim=128）、other 按 **token**（cols=128）；V 相反。⇒ **一页（64 token）根本不是一个量化单元**，页内任何一个轴条目都依赖另外 64 个 token。
- **判据 2（未封口时平面里是陈旧值）**：`kvarn128_encode_kernel` 只在 `t.sealed` 时写码流平面（`:129` `if (!t.in_range || !t.sealed) { return; }`），未封口的 token 只在 stage 里（`:80-116` rotate）。⇒ 未封口 tile 的 plane 内容是**上一次封口留下的**，任何"从平面读轴"的路径对未封口 tile 都会读到错值。
- **判据 3（现状怎么绕的）**：`kvarn128_window_kernel:190-225` 分两支——`t.sealed` 走真解码，未封口**从 stage 取旋转域原值**；且 stage 是"**这块 tile 的旋转域累积值**"而不是"本次 append 的暂存"（`kvarn128_launch.cu:261-268` 的实测记录：用全局 stage 时未封口窗口的保持段 `[0,51)` 被 51/51 个 token 覆盖，cos 从 1.000000 掉到 −0.237~−0.103）。
- **⇒ 硬约束**：跨页取维轴（方案 B）与"维轴独立 plane"（方案 C 的拆 plane）都**只在 sealed tile 上成立**；未封口分支必须继续走 stage。这条不因几何改变而放宽，且新几何的窗口写侧必须保留同样的两支（`kvarn128_window_kernel:165` 的 `hi = t.sealed ? 128 : t.tt_end`）。

### 4.5 `valid_tokens(width)` 上界

- **判据**：`PagedKVDirectMetadata::valid_tokens(width)` 直接返回 `width`（`paged_kv_address.cuh:17`）；`PagedKVBatchMetadata<Masked>::valid_tokens(width)` 取 `valid <= 0 ? 0 : min(valid, width)`（`:29-35`），`valid_columns` 在 `Masked=false` 时可以是 `nil`（`KVarN全档位移植/04-K4V2_g128存储路径.md:18` 记载这是被误杀过的点）。
- **对 KVarN 的含义**：KVarN 的 append **完全不看 `valid_tokens`** —— 它自己在 device 上按 `positions[0] / positions[count-1]` 推 tile 与 `tt_begin/tt_end`（`kvarn128_launch.cu:58-73`）。所以 `valid_tokens` 是**消费侧**（bf16 镜像）的上界，不是 KVarN 的写侧上界。
- **对新几何的约束**：KVarN 的"有效 token"上界由 `tiles_span = tokens/128 + 2`（`:820`）与 `r.tile <= tlast`（`:66`）共同给出，`+2` 是**上界而不是精确值**（跨 2 个 tile 时的余量）。任何新几何若把"一条 record"的边界从 128 改成别的值，这两个上界必须同步，否则会出现"该封口的 tile 没被访问到"的静默漏写。

## 5. 三种做法的改动面与风险排序

### 5.1 三种做法的精确定义（先定义，避免歧义）

三种做法**都指向同一组字节数**（280 / 248 / 216），差别在机制：

| 方案 | 机制 | 是否保留"页自足" | 是否保留"64-token 页 + 稠密 plane" | 是否改 plane 数量 |
|---|---|---|---|---|
| **A 紧凑 blob** | 一条 128-token record（K/V 各 2 slice × 8960 B）连续落盘，彻底放弃 64-token 页平面几何 | 不适用（无页） | 否（需要新存储类） | 是（或另立存储类） |
| **B 跨页取维轴** | 保留 4-plane 与 64-token 页，维轴只在 tile 的**偶数页**存一份，奇数页读者跨页读 | **否**（破坏） | 是 | 否（但需 sibling 通道） |
| **C 维轴降位/拆 plane** | 保留页自足与 64-token 页，把**维轴条目**从 FP16 换成 U8（16→8 bit）⇒ scale 区 36 B → 24 B | **是**（保留） | 是 | **是**（4 → 6，因一个 plane 只能一种 dtype，L12/L13） |

**C 的字节算术（逐项）**：每 token 每 head 的 scale 区 = 维轴 12 half（K scale 4 + K zp 4 + V other 4）+ token 轴 6 half（K other 2 + V scale 2 + V zp 2）= 18 half = 36 B。
维轴降为 1 B/条 ⇒ `12×1 + 6×2 = 24 B` ⇒ 总字节 `32·(Kb+Vb) + 24` = **280**（与紧凑口径同值，但**页自足仍在**，代价是维轴精度 16→8 bit）。

### 5.2 先否掉两条常见说法（有判据）

1. **"P2：维轴只存偶数页 ⇒ 222 B/token"不成立**。判据：`plan_device_kv_page_pool:103-113` 建的是稠密张量 `{leading_extent, kPagedKVPageSize, head_extent, physical_pages}`，`leading_extent` 是**该 plane 所有页共用的常量**，并且被 `paged_kv_address.cuh:47-53` 直接当 stride 用 ⇒ 页内字节数恒定。"只在偶数页写维轴"只让奇数页的那几列变成未使用，**分配字节一字节都不减**。（`接线细案-20261013.md:162` 的 28,416 B/tile 与 222 B/token 出自该文自述的"派生规则"，同文 `:435` 已把它列为"未确认"。）
2. **"砍 12 B 冗余"不会掉精度、也不是近似**。判据：P1 两页的维轴两份**值逐位相同**（同一份 `sa/zp/oa` 写两遍，`kvarn128_codec.cuh:284-304`）⇒ 去重复是恒等变换。所以**方案 B 的数值风险为零，风险全在寻址与页语义**；**方案 C 的数值风险不为零**（维轴真的从 16 bit 降到 8 bit），这是它唯一的代价。

### 5.3 改动面与风险排序

| 方案 | 改动 tag（§3 编号） | 条数 | 主要风险 | 风险等级 |
|---|---|---:|---|---|
| **A 紧凑 blob** | L01–L10、L11–L16、L17–L24、L25–L34、L35–L40、L41–L45、L46–L49、L57–L60（几乎全表，除 L50–L56 的解析/日志类） | **≈58** | ① 一条 record 跨 2 页，而**逻辑页→物理页是任意映射**（`paged_kv_cache.cpp:1122-1137`）⇒ 必须引入"tile 的两页物理相邻"或新的页分配语义；② `validate_geometry:41-43` 硬钉 64-token 页；③ 前缀缓存块粒度 64（`block_hash.h:11-13`）与 128-token record 冲突；④ 需要新存储类，`d256_profile`/`paged_kv_storage_layout` 全分支都要新增 | **高** |
| **B 跨页取维轴** | L05、L06、L07、L08、L09、L11、L14、L15、L21、L22、L23、L24、L27、L31、L33、L34、L36、L37、L41、L42、L57 | **≈21** | ① 公共寻址式无 sibling（`paged_kv_address.cuh:63-69`）⇒ 要么改全引擎寻址式，要么新增 sibling 表（capture 前预分配，撞 4.2）；② **放弃页自足**（`kvarn_layout.h:18-20` 的取舍被推翻）；③ 未封口分支仍必须走 stage（4.4） | **中** |
| **C 维轴降位/拆 plane** | L05、L08、L11、L12、L13、L15、L17、L18、L21、L25、L35、L36、L37、L40、L59 | **≈14** | ① 一个 plane 只能一种 dtype ⇒ 必须把 scale 拆成"维轴 U8 plane + token 轴 FP16 plane"，plane 数 4→6，`planes_per_layer`（`paged_kv_storage.h:39-42`）与 `decoder_state.cpp:48` 两处硬编码要同步；② **维轴 16→8 bit 是真实精度损失**，需 PPL 判据（K 的 scale/zp 是每维量化参数，不是列因子）；③ 页内寻址式不变（`leading` 的**槽位数**不变，只变 dtype），风险面最小 | **低–中** |

### 5.4 推荐

**推荐方案 C，且前置条件是"窗口改造已验收"。** 理由与条件：

1. **先修窗口，再谈几何**。当前亏空是 4.25 GiB 的 bf16 全量窗口（`kvarn128-验收-20261014.md` 第 3 节），几何改造的全部收益是每档 12 B/token（327,680 ctx × 4 head 下 K4V2 也只值 15 MiB）。**收益与亏空差两个数量级** ⇒ 顺序不能反。
2. **不要为 K4V4 做几何改造**。紧凑 K4V4 = 280 = 生产 280（±0），K4V4 档下三种做法都是零收益。几何改造只在 **K4V3（−11.43%）与 K4V2（−22.86%）** 这两档才有意义；而 P1 已经给出 K4V3 −7.14% / K4V2 −18.57%。
3. **选 C 不选 B**。B 的数值风险为零但**牺牲页自足**这条已写进设计文档的取舍（`kvarn_layout.h:18-20`），且要动全引擎公共寻址式或新增 sibling 表（撞 capture 约束）；C 保留页自足与稠密 plane，只改 dtype 与 plane 拆分，**14 条**改动且寻址式不变。
4. **选 C 不选 A**。A 的 58 条里最贵的是"record 跨两页 × 物理页任意映射"（`paged_kv_cache.cpp:1122-1137`）——这不是改几行能解决的，需要新的页分配语义。除非目标变成"与上游逐字节同构"（便于对拍与移植上游新档位），否则 A 的复杂度不值得。
5. **C 的验收判据必须写死**：改完后 `--kv-dtype kvarn128` 在语料 A/B 上 `Δ_rk4v4 ≤ +0.10%`（沿用 `kvarn128-验收-20261014.md` 第 1 节口径，当前是 −0.0325% / −0.0166%），且 `327,680 ctx × 4 head` 的 KV 账从 365.0 MiB 降到 350.0 MiB。**达不到就退回 P1。**
