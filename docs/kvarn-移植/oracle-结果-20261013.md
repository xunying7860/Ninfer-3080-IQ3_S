## 结论先行

1. **36 格字节账：doc02 的表与 `make_layout` 逐格完全一致，36/36、0 差异。** 但 `make_layout` **不是**
   D256 下真正分配 arena 的口径（它在本仓只有一个调用者：`tests/test-kvarn.cpp`，且只用 `head_dim=128`）。
   真正决定字节数是 `make_record_layout × head_slices`，对 D256 而言 = **doc02 每格 + 6 B/token**。
   ⇒ **K4V2 的正确字节是 216 B/token（不是 210）；K4V4 = 280（不是 274）**。
2. **G128 相对 G64 的量化误差：K 略变差、V 略变好，两者都是 1e-4~3e-3 量级，方向相反、互相抵消** ⇒
   实测两档 **K cos −0.00042（K4V2 与 K4V4 相同）/ V cos +0.00018（K4V4）~+0.00270（K4V2）**。
   净判断：**G128 用 12 B/token 的账换来的质量变化在噪声量级，没有可测的质量代价**（但也没有质量收益）。
3. **这份 oracle 可以当唯一基准，但要打一个补丁**：算法部分（Sinkhorn + per-row RTN + 位串 + record 三轴）
   已与上游三处交叉对齐（fp16 转换器 vs nvcc 0/6,000,021 不一致；GPU 口径 vs CPU 口径 scale 差 ≤8.3e-7；
   位串 6 个位宽 0 失败）；**不能**当基准的是"210 B/token"这个数——它来自死路径。
4. 顺带查清 doc02 §2.1 自己挂着的"768 B 差异必须查清"：**768 B = 6 B/token，来源是 record 口径把
   `other_axis`（列因子）按 slice 各存一份（2×128 项），而 `make_layout` 只存一份（128 项）**。
   D128（head_slices=1）时两者**逐格相等**（已验 36/36），证明这不是公式写错，是 D256 多 slice 的结构差。

### 1.2 为什么"record 口径"才是真口径（四条硬证据）

**(a) 上游有一句 GGML_ASSERT 把 arena 的每记录字节锁死在 record 公式上**（`ggml/src/ggml-cuda/kvarn.cu:2229-2240`）：

```c
const int record_dim = int(stage->ne[0]);
GGML_ASSERT(record_dim == 64 || record_dim == KVAR_N_DIM);
const int record_rows = value ? KVAR_N_DIM : record_dim;
const int record_cols = value ? record_dim : KVAR_N_DIM;
const size_t expected_record_bytes = size_t(record_rows * record_cols * bits) / 8 +
    size_t(2 * record_rows + record_cols) * sizeof(half);
GGML_ASSERT(records->ne[0] == (int64_t) expected_record_bytes);   // <- 硬约束
```

**(b) arena 张量就是按 `record_bytes × (n_head_kv · head_slices)` 开的**（`src/llama-kv-cache-kvarn.cpp:1482-1500`）：

```c
const int k_slices = int(k_geometry.head_slices);            // D256 -> 2
const size_t k_record_size = kvarn_record_bytes(k_record_dim, this->params.key_bits, false);
const uint32_t n_head_k_sliced = n_head_kv * (uint32_t) k_slices;      // 4 * 2 = 8
auto * k_records = ggml_new_tensor_3d(ctx, GGML_TYPE_I8, k_record_size, n_head_k_sliced, n_record_groups);
```

`kvarn_record_bytes()` 是 `llama_kvarn_make_record_layout(...).record_bytes` 的一层薄封装（同文件 :303）。

**(c) `make_layout` 在我抓取的 5 个 KVarN 相关文件里没有任何调用者**：`src/llama-kvarn.cpp`、
`src/llama-kvarn.h`、`src/llama-kv-cache-kvarn.{h,cpp}`、`ggml/src/ggml-cuda/kvarn.cu` 五处全文检索
`llama_kvarn_make_layout` 只命中"定义 + 声明 + 结构体"；全仓唯一调用者在 `tests/test-kvarn.cpp`，
且两处都写作 `llama_kvarn_make_layout(128, 128, ...)`（**head_dim=128**，不是 256）——即连测试
都没走过 D256 那条分支。

**(d) 数值自证——D128 时两口径逐格相等**（说明 768 B 不是公式错，是多 slice 的结构差）：

```
== D128 (head_dim=128, head_slices=1): make_layout vs record ==
  全部相等: True  (K4V4: mL=17920 rec=17920 = 140 B/token)
== D256 (head_slices=2) 差从哪来 ==
  K: make_layout=17664 record=17920 差=256 ; K 轴条目数 mL=640 rec=768
  V: make_layout=9216 record=9728 差=512 ; V 轴条目数 mL=512 rec=768
  合计差 = 768 B  (= 6 B/token x 128)
```

**结构解释**：record 里 K 的 `other_axis`（列因子）按 slice 各存一份（2 slice × 128 项 = 256 项），
而 `make_layout` 的 `k_s_row` 只存 group 一份（128 项）；V 侧的 `v_s_col`/`v_s_row` 同理。每 head
每 group 多出 128(K) + 256(V) = 384 项 × 2 B = 768 B = 6 B/token。

### 1.3 与"旧引擎实测口径"接得上，而且互相印证

旧档案 `预筛-首轮结果-20261012.md` §30 用两条独立引擎路径实测过（`d256_kv_cache_profile` +
`paged_kv_storage_layout().physical_bytes_per_token_head()`）：

```
K4V2: 旧引擎 G64 实测=228  beellama record=216  差=-12 B/token (-5.3%)
K4V4: 旧引擎 G64 实测=292  beellama record=280  差=-12 B/token (-4.1%)
```

注：这两个"旧"值是 §30 实测值（228 = K 146 + V 82；292 = K 146 + V 146），不是我推算的。分解：
`146 = 128 码 + 9 槽×2 B`（旧 codec 每 token 9 个 fp16 侧信息）→ record 口径是 `128 码 + 6 槽×2 B = 140`
（6 = 2 slice × 3 轴），**每侧省 6 B/token、K+V 省 12 B/token**。

而口径①（`make_layout`）给的是 210/274，比旧引擎实测值低 18 B/token，等于把收益夸大了一倍。

**一个强交叉印证**：口径② 下 **K4V4 = 280 = 生产 `rk4v4` 的 280 完全相等**（零收益、零代价），
这正是 `05-全档位实现.md` §5.3 独立给出的"K4V4 = 零字节代价验证点"；而口径① 会说 K4V4 = 274（−2%），
与它自己的结论矛盾。→ 口径② 自洽。

### 1.4 对 doc 00/02 的更正建议（三个数）

| 项 | doc 现值 | 应改为 | 依据 |
|---|---|---|---|
| K4V2 B/token | 210（−25%） | **216（−22.9%）** | arena 口径 |
| K4V4 B/token | 274（−2%） | **280（±0%）** | arena 口径；= 生产 rk4v4 |
| 327,680 ctx / 4 KV head 的 K4V2 池 | 262.5 MiB（省 87.5） | **270.0 MiB（省 80.0）** | 327680×216×4/1024² |

`record_bytes = rows*cols*bits/8 + (2*rows+cols)*2` 这条公式本身**没错**，错的是往里代
`rows=head_dim=256, cols=group=128`（那是 `make_layout` 的摊法）；arena 里 K/V 都代
`rows=cols=128`（`record_dim`），乘 `head_slices=2`。

## 三、量化→反量化误差（真实数据 + 合成数据）

数据：`layer35/63_{k,v}_proj.pt`（256 token × 4 head × 256 dim，2 层），按 beellama D256 口径
旋转（逐片 WHT128 × 0.08838834764831845，跨片 Hadamard × 0.7071067811865475）后切 128×G 的 slice。
指标：**原向量 vs 反量化向量**的 cosine（K 的 token 向量 = 列、V 的 token 向量 = 行），`relL2 = ‖Δ‖/‖orig‖`。

### 3.1 三档必测（真实数据）

| 配置 | K cos_glob | V cos_glob | K relL2 | V relL2 | 每 tile 记录字节 |
|---|---:|---:|---:|---:|---:|
| **K4V2_g128** | 0.9980798 | 0.8917075 | 0.06204 | 0.51212 | 27648 B/128 token |
| **K4V4_g128** | 0.9980798 | 0.9948118 | 0.06204 | 0.10199 | 35840 B/128 token |
| **K4V4_g64**（对照） | 0.9985019 | 0.9946277 | 0.05474 | 0.10352 | — |

K4V2 与 K4V4 的 K 数字逐位相同（两者 `bits_k` 都是 4）——这是 oracle 的自洽性检查，通过。

### 3.2 G128 相对 G64 的误差变化（真实数据，同一 128-token 范围）

| 档 | K cos 变化 | V cos 变化 | K relL2 | V relL2 |
|---|---:|---:|---|---|
| K4V2 | **−0.0004221** | **+0.0026976** | 0.05474 → 0.06204 | 0.51918 → 0.51212 |
| K4V4 | **−0.0004221** | **+0.0001841** | 0.05474 → 0.06204 | 0.10352 → 0.10199 |

**回答"变好还是变差"：没有单向结论，两侧反号。**
- **K 变差 ~4.2e-4**：K 是 per-channel（按 dim 行）RTN，量化区间跨 **token 轴**；组从 64→128 使
  per-channel 的 min/max 区间变宽 ⇒ 步长变大 ⇒ 略粗。这是结构性、可解释的，且与数据无关（合成数据同号）。
- **V 变好 ~1.8e-4（K4V4）/ +2.7e-3（K4V2）**：V 是 per-token RTN（跨 dim 轴），组大小**不改变**每 token
  的量化区间；G128 唯一的作用是让**列因子**（每 dim 的 s_col）由 128 个 token 而不是 64 个估计出来 ⇒ 更准。
- 合成数据上 V 这一项反号（gauss K4V4：0.9952019→0.9951330，−7e-5；outlier K4V4：0.9939455→0.9935130，
  −4e-4），量级都 ≤1e-3，说明 V 侧这一项本身就在噪声量级内。

**净话术**：G128 省 12 B/token（见 §1.3，与旧引擎实测 292/228 比），质量上换来的是
`K −4e-4 / V +2e-4~+3e-3`（真实数据），两侧反号 ⇒ **无可测的质量代价，也无质量收益**。

### 3.3 合成数据（高斯 / 带离群通道）

### 3.4 与旧档案数字的关系（必须说清，否则会误读）

- 本表是 **"原向量 vs 反量化"** 的 cosine。
- 旧档案 §22/§23/§29 里的 `0.9997882 / 0.9998246 / 0.9989311 / 0.9992736` 是
  **`cos(host 全链, kernel 平面解码)`**，即 codec-对-codec 的数值一致性，**不是重建质量**，两者不能比。
- 旧档案 §30/§31 的 `attn cos 0.9486 / 0.9497 / 0.9919` 才是质量口径，但那是**注意力输出**的 cosine，
  也不是 V 向量 cosine。
- ⇒ 旧 G64 codec 与本次 G128 codec 之间**没有可直接比较的历史数字**；能比的只有"同一份 oracle、
  同一份数据、只差 group"的 §3.2 那个差值。
- 唯一可比的定性结论：**V 2-bit 很差（V cos 0.8917，relL2 0.51）**，这与 beellama 自己的推荐阶梯
  （`kvarn4/kvarn3` 是最小推荐档，见 doc 01 §5）和旧档案 §30 的 `K4V2 attn 0.949658` 方向一致。
  **本 oracle 不支持把 V 定到 2-bit。**

## 六、判据："如果只信一份基准，是不是该信我这份"

**该信，且应该同时把它当成阶段 2 的 kernel 验收标尺。判据：**

1. **不是二手资料**：直接抓了上游 4 个源文件（sha256 已记），算法逐行对照而非按文档转述；
   doc 03 里没有的 `kvarn_update_best_from_std` / `kvarn_reduce_std_ranges` / CPU 侧
   `variance_normalize` 我都是从原文抄的（否则 imbalance 判定只能靠猜）。
2. **可自证**：fp16 转换器与 nvcc 逐位对拍 6,000,021 个值 0 不一致；位串 6 个位宽往返 0 失败；
   两个独立口径（GPU / CPU）互相校准到 1e-6。
3. **可复现**：一条 docker 命令 + 固定种子，`out/*.txt` 是原始输出，报告里每个数字都能在 `out/` 里找到出处。
4. **它抓到了别人没抓到的东西**：doc02 的 36 格是 `make_layout`（**本仓只有测试调用者的路径**），
   D256 真字节 +6/token；且这一更正让 `K4V4 = 280 = 生产 rk4v4`、与 doc 05 §5.3 的"零字节代价"自洽，
   同时与旧引擎 §30 实测 292/228 严丝合缝。
5. **它敢说不知道**：见下节。

**它不该被当基准的三处（如果你只信一份，也要知道这份的缺口）：**

1. **WHT 旋转未与 ninfer 对拍**（doc 03 §3.9 的开放项）。本 oracle 的旋转照 `kvarn.cu` 写法实现，
   但"ninfer 的 `normalized_hadamard_d256_inplace` 是否与之数值等价"没验。codec 与旋转无关，
   但这个缺口会影响端到端数字。
2. **G64 臂不是旧 codec 复刻**：beellama 的 `token_group` 是编译期常量 128，`make_record_layout`
   签名里根本没有 group 参数 ⇒ 我是把同一 codec 的 token 轴推广到 64（std 分母同步用 n−1）。
   这是"同口径不同组"的干净对比，但**不能**当成 ninfer 旧 G64 codec 的复刻。
3. **3/5/6-bit 只验了"CPU 实现 vs 每行打包等价"，没有 GPU 实测可比**（上游也没有 3/5/6-bit 的公开对拍数据）。
   位序一致性有代码级证据，没有真机证据。

⇒ **结论**：把它当"数值基准/唯一真值来源"，可以；但阶段 2 的验收必须补两件事：
（i）CUDA kernel 输出与 `bee_quant_tile` 逐字节对拍（本 oracle 已能 dump 整条 record，直接比字节）;
（ii）WHT 与 ninfer 既有实现的数值对拍。在补完这两项前，**不要**用它的绝对误差数字去下"质量够不够"的结论——
§3.4 已经说明本表口径与旧档案的质量数字不可比。
