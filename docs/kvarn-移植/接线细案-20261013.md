### 2.2 轴语义（决定 scale plane 的内容）

`03-K4V2_g128量化kernel.md` §3.7 定死：
```
other_axis[row] = __float2half_rn(best_col[row]);           // 列因子
scale_axis[row] = __float2half_rn(best_row[row] * scale);   // 行因子 × 行 scale
zp_axis[row]    = __float2half_rn(best_row[row] * lo);      // 行因子 × 行 lo
```
配合 §3.8 的 `token = value ? row : col` ⇒
- **K**：row = dim，col = token ⇒ `scale_axis`/`zp_axis` 是**每维**向量，`other_axis` 是**每 token**向量。
- **V**：row = token，col = dim ⇒ `scale_axis`/`zp_axis` 是**每 token**向量，`other_axis` 是**每维**向量。

反量化是 rank-1 外积：
- K: `k[d,t] = (code[d,t]·scale_axis[d] + zp_axis[d]) · other_axis[t]`
- V: `v[t,d] = (code[t,d]·scale_axis[t] + zp_axis[t]) · other_axis[d]`

### 2.3 推荐几何（**页自足方案 P1**）：页 = tile 的 1/2，维轴在两页各存一份

| plane | dtype | `leading_extent`（元素） | 页内元素账（K4V2，D256，2 slices） |
|---|---|---|---|
| `k_pages` | `U8` | **8192** | 64 token × 256 dim × 4 bit / 8 = 8192 B |
| `v_pages` | `U8` | **4096** | 64 token × 256 dim × 2 bit / 8 = 4096 B |
| `k_scale_pages` | `FP16` | **640** | 维轴 (scale+zp) 128×2×2slice = 512 + token 轴 64×2slice = 128 → 640 half = 1280 B |
| `v_scale_pages` | `FP16` | **512** | 维轴 (other) 128×2slice = 256 + token 轴 (scale+zp) 64×2×2slice = 256 → 512 half = 1024 B |

`value_leading_extent` 用 §1.3 新加的字段表达（K/V 位宽不同，`leading` 也就不同）；`quant_group = 128`。

**代价（必须写进决策点）**：per tile per head = (8192+1280+4096+1024)×2 = **29,184 B / 128 token = 228 B/token/head**。
- 对照：`02-字节账与偏移表.md` §2.1 的 `make_layout` 口径 **210**（26,880 B）；`record 布局` 紧凑口径 **216**（27,648 B，`02` §2.1 原文：「合计 27,648，与 make_layout 的 26,880 差 768 B。这个差异必须查清」）。
- 多出的 12~18 B/token 全部来自 **页槽位统一 + 维轴按页存两份**（页内 64-token 粒度装不满一个 tile 的轴）。
- 对 280 B 的生产 `rk4v4`：**省 18.6%**（不是 25%）。327,680 × 4 head ⇒ 285 MiB vs 350 MiB，省 **65 MiB**。

**备选 P2（跨页取轴）**：~~维轴只存偶数页 ⇒ 28,416 B/tile = 222 B/token~~ **已否证（2026-10-14 读代码核实）**：`src/core/paged_kv_cache.cpp:103-113` 建的是稠密张量 `{leading_extent, 64, heads, pages}`，`src/ops/kernel/paged_kv_address.cuh:50-52` 把 `leading_extent` 当**全局 stride**（寻址式里没有 sibling 页项）⇒ 页内字节恒定，只在偶数页写维轴**一字节都不省**；真要跨页借数据，必须先给寻址式加 sibling 项。详细见 `紧凑几何设计-20261014.md`。

**未确认**：P1/P2 与 `make_layout` 的差额归属（`02` §2.1 的「行动项」）——本档只给派生规则，**精确值待标量 oracle**（`07-验证与对撞.md` §7.2）。

- **`04` §4.5 的双槽不是性能冗余**：原文「单 slot 会产生静默错误（不报错、内容错）」，且「你的 `--spec mtp` 被拒 draft 回滚正好走这条」。
- slot 索引编码照抄 `04` §4.4 的 int64 打包（slot 1-based）；`E:src/ops/kv_cache/append/kvarn_launch.h` 未见该函数，说明旧路线**没做**这一步 —— 这是新路线的新增项。

## 6. 1 tile = 2 pages 的页表与偏移方案

### 6.1 分配侧（`src/core/paged_kv_cache.cpp` + planner）

- **`P:src/core/paged_kv_cache.cpp:274 DeviceKVPagePool::capacity_pages()`** 与 `:267-271` 的 free list：整池一段 `KVPageRun{0, page_group_count}`。**成对分配必须新增口径**：`KVPageRun` 是「连续物理页的段」（`:88-93` 注释「The free list is kept sorted and coalesced, so a run is the natural unit」）⇒ **核心不变**，但 `reserve()/materialize()`（`:272/:283`）要保证 **pair 不被拆**（偶数起始、`count` 偶数）。
- **页数必须是偶数**：`P:src/models/qwen3_5/state/decoder_state.cpp:13 page_count()` = `1 + (capacity-1)/64`。`04` §4.6 指定「`--kv-capacity` 取整到 128 倍数；327,680/128 = 2,560 tiles」。⇒ 在 `page_count` 或其调用点（`P:src/models/qwen3_5/program/planning/startup.cpp:995` 的 `page_count(options.kv_capacity.explicit_tokens)`）对 KVarN 做 **128 对齐**；并把 `logical_pages` 向上取偶。
- **物理页数**：`P:.../startup.cpp:81 maximum_main_page_groups(...)` / `:183-190` 传到 planner；`P:.../decoder_state.cpp:35` 校验 `physical_page_groups >= logical_pages`。KVarN 下**也应取偶**（否则最后一页组无法配成 tile）。
- **prefix cache 对齐**：`04` §4.6「prefix cache 对齐到 128（tile）而非 64（page）」⇒ 落点在 `P:src/models/qwen3_5/program/planning/startup.cpp:531/:678`（`page_count(plan.capacity)` 与 width/batch 的 workspace 规划）。
- **`--prefill-chunk`**：`04` §4.6「1024/128 = 8 tiles ✓ 整数倍」；冒烟加 non-128 倍数（`04` §4.6 建议 `1000`）。

### 6.2 逻辑→物理映射

block table 仍是 `[logical_pages, table_rows]`（`P:src/core/paged_kv_cache.cpp:126-130`），**只把逻辑页的解释改成「半 tile」**：
```
position → logical_tile = position / 128
         → logical_page = 2*logical_tile + ((position % 128) / 64)
         → physical_page = block_table[logical_page]        // 偶数起始
         → in_tile_page_offset = position % 64
```
**tile 起始页必须偶数**（`04` §4.6）。因为两页同一 tile，读 C 路径（跨组封口）与消费端都要能**从任意一页找到另一页**：
```
tile_even_page = physical_page & ~1        // 或 block_table[logical_page & ~1]
sibling_page   = tile_even_page ^ 1
```
**为什么这个做法成立**：`P:src/core/paged_kv_cache.cpp:104-107` 是 page-major 布局，同 head 的两页在内存上相距 `64*kv_heads*leading`，**不连续**；`paged_kv_element_offset`（`P:src/ops/kernel/paged_kv_address.cuh:55-61`）按「单个物理页 + page_offset 0..63」寻址，所以**不能**靠「base 页 + page_offset 0..127」拼接，必须显式算 sibling 页。

**偏移公式（P1 方案）**：新增
```
paged_kv_kvarn_offset<tile_leading, head_extent>(block_table, head, position, leading_idx)
  = paged_kv_element_offset<tile_leading, head_extent>(
        paged_kv_physical_page(block_table, position),   // 物理页
        head,
        position % 64,                                    // 页内偏移
        leading_idx)
```
与现有 `paged_kv_element_offset(block_table, head, position, leading)`（`:63-69`）**同形**，只是把「tile 的轴向量在页内的落位」交给 `leading_idx` 的编码（§2.3 的 640/512 元素账）。**P1 下每页自足，所以不需要 sibling 页**——这是选 P1 的主要理由。

### 6.3 未满 tile（<128 token）

- **B 路径**：写 F16 stage，**不产生 record、不写任何 plane**（`04` §4.3 表，B「不需要 block-table」）。`tokens=51` 落 B（`04` §4.3 末：「你的 `tokens=51`、`columns=51` 应落在 B（若 off=0）」）。
- **C 路径**：`off + n >= 128` 时先封口 `[base, base+128)`，余量递归；需要 table_rows 定位目标 tile 的偶数页。
- **stage → plane 的写目标**：A/C 的编码 kernel 用 §6.2 的 offset 写 `k_pages/v_pages/k_scale_pages/v_scale_pages` 四个平面；`04` §4.6 指定「同 tile 的 128 token 共享一条 record 头」⇒ 落点在新增的 `paged_kv_window.cuh`（新文件），旧路线无此文件。
- **decode（单 token）**：恒为 B，只写 stage；页/tile 满时由后续 append 触发 C。

### 6.4 容量账校验点

`327680 tokens / 128 = 2560 tiles = 5120 pages`；当前运行实例的 `pages 1,024/1,024`（`实机取证` §1）是 65,536 token 档，对应 512 tiles/1024 页 ⇒ **页数与 token 数的 64 关系不变**，tile 只是把 2 页绑成一组。

## 7. 消费端读路径（**不靠 bf16 mirror**）

### 7.1 旧路线为什么死

```
实机取证-20261013.md §10：同一二进制只换 KV_DTYPE，rk4v4 6/6 正确、kvarn（K4V4）6/6 退化、
                          kvarn2（K4V2）6/6 退化；两进程结果互不一致。
实机取证-20261013.md §11：mirror 的数值正确性从来没有被对拍过；harness 只验过「码→解码」。
```
旧路线的 mirror 写点三处（`E:src/ops/kv_cache/append/kvarn_prefill_kernel.cuh:120-139` 满瓦片反量化值、`:57-67` 尾瓦片原值、`:180-181/:220-236` decode）口径必须与「未旋转域 bf16 attention」一致 —— 这一层旋转/折叠口径**从未验证**。新方案**不再引入 mirror 这一层**。

### 7.2 选定的范式：量化域 rank-1 解码，骨架照 `prompt_i8`/`small_t_i8`

**数学分解**（`05-全档位实现.md` §5.6 原文）：
```
K 侧： k[d,g] = (qc[d,g]·s_col[d] + zp[d]) · s_row[g]
       logit[g] = s_row[g] · ( Σ_d (q[d]·s_col[d])·qc[d,g] + Σ_d q[d]·zp[d] )
V 侧： v[g,d] = (vc[g,d]·s_row[g] + zp[g]) · s_col[d]
       out[d]  = s_col_V[d] · ( Σ_g (p[g]·s_row_V[g])·vc[g,d] + Σ_g p[g]·zp_V[g] )
```
（`05` 用的记号 `s_col/s_row` 对应本档 §2.2 的 `other_axis`（列因子，预乘到 Q 或 softmax 权重）与 `scale_axis`（行因子）。`zp` 在 K 侧是 `zp_axis[d]` 与 `s_col` 的标量对，在 V 侧是 `zp_axis[t]` 与 `s_col` 的标量对。）

**选它的出处与理由**：
- 引擎侧同范式已在跑：`P:src/ops/softmax_attention/dense/causal_cache/prompt.cu:144`（`kv_cache_is_int8_family` 分支的 `causal_attention_prompt_i8_kernel<Geometry, Metadata, PackedValues, Keys, PvF16, PackGqa>`），`P:.../prompt_i8.cuh` / `small_t_i8.cuh` 就是「int 码 + 平面上的 scale → logits」的现成骨架。
- `05` §5.6 明确「ninfer 不该照抄 beellama 的 materialize；ninfer 的 rk8v4 本来就在量化域做 QK」⇒ 直接走量化域。
- **两条路径都保留**（`05` §5.6 第 1/3 条）：先按 beellama materialize（`kvarn.cu:2780 live kernel` / `:3088 op`）写一个**只用于验证 codec**的物化 kernel，再用环境变量切到快路径，便于回归。

**与 int8 family 的关键差别（决定「必须自己的 kernel」）**：
| 项 | int8 G64 | KVarN G128 |
|---|---|---|
| scale 平面读法 | 每 token 4 组（`P:src/ops/kv_cache/int8_g64_codec.cuh:33-38`，`Groups = 256/64 = 4`） | K：每维 1 组 + 每 token 1 列因子；V：每 token 1 组 + 每维 1 列因子（§2.2） |
| Q 预处理 | 旋转 + 组内 scale | 旋转 + **`s_col[d]` 预乘**（`05` §5.6） |
| 码宽 | 8-bit（或 packed int4） | 2/3/4/5/6/8-bit 位串（`05` §5.1） |
| 组粒度 | 64 dim | 128 token（组 = tile） |

⇒ **不能复用 int8 的 scale 读法**；**能复用的是 kernel 骨架**（网格/分片/softmax 归约/`pack_gqa`/动态 smem opt-in 那条 `cudaFuncSetAttribute` 形态，`P:.../prompt.cu:158-162`）。

### 7.3 旋转：`normalized_hadamard_d256_inplace` 不能默认等价

```
P:src/ops/kv_cache/hadamard_d256.cuh:46  __device__ __forceinline__ void normalized_hadamard_d256_inplace(float (&values)[8], int lane) {
```
ninfer 的是**整 D256**归一化 FWHT（末级 `__fmul_rn(value, 0x1p-4f)`，`:64`）与 `hadamard_d64_fragment_inplace`（`:27`）。
beellama 是 `kvarn_wht_128`（128 点）+ `kvarn_wht_cross_slices`（跨 slice 混合，D256 ⇒ `head_slices=2`，`03` §3.9 原文「D256 你就是 2 slices，这一路必须实现」）。
**两者维度不同**（128+跨片 vs 256），**不默认等价**（`03` §3.9 原文「不要默认等价」）。**判据**：`07` §7.2 的标量 oracle 逐字节比（先比 `kvarn_wht_128 + cross_slices` 与 `normalized_hadamard_d256_inplace` 的输出；若一致 ⇒ 复用 ninfer 的，省一次 GEMM）。

### 7.4 三处消费端落点（必须新增分支，否则掉 bf16，见 §4）
