# KVarN 移植（任务 A）收单：冻结，及其全部实测依据（2026-10-14）

> 用户拍定：**冻结这条线**（K4V4 零收益；V 侧最好候选也不投算力）。本文是收单件：结论、数字、资产清单、未决项、现场合规，一次写清。

## 0. 结论先行（三条，都有原始数字）

| 问题 | 判定 | 依据 |
|---|---|---|
| KVarN `kvarn128`(K4V4) 能替生产 `rk4v4` 吗 | **不能，零收益** | 引擎 PPL 打平略优（vs `rk4v4` −0.0325%/−0.0166%），但字节 **280 = 280**；显存上还靠窗口修复才把 **倒亏 4.43 GiB** 抹平（§2）；吞吐更差（32K TTFT **+39%**、prefill **−28%**） |
| V 侧还有没有"真省字节"的改法 | **只有一个可判定候选，且不划算** | `K4Vprom_k32`（V 通道为行 3bit + 逐 tile 提 32 个通道到 4bit）**252 B**，三语料同号 +0.1224/+0.0564/+0.1046、摆幅 0.0660%（全场唯一小于判据），合并 11,392 token 精确重算 **+0.0837%** ⇒ 含义是"省 10.0% KV 字节（≈590 MiB）换 +0.08% 量级劣化"，而代价还要再加 prefill −28% |
| KVarN 比 llama.cpp 原生 KV 档更好吗 | **K 侧略胜、V 侧不占优，且不构成替换理由** | 同字节下 K 侧赢集合内最好的 `iq4_nl` **+0.00198**；V 侧**连不旋转的 `iq4_nl` 都赢它 +0.00132**；唯一在 V 侧赢过它的 `q4_K` 在 llama 里**不能用于 KV**（§3） |

**判据分辨力**：语料只有 2,944 / 6,016 / 2,432 scored token，合并 11,392；同臂跨语料漂移 0.066%~0.336%，与 +0.10% 判据同量级 ⇒ **这套 oracle 在 0.1% 档上分辨力不足**，这是"不再投算力"的第二个理由（要判 0.10% 得把评测集再放大一个量级）。

## 2. 显存与吞吐（决定"省显存"这笔账）

- 改前病灶：`KVarN128 窗口已分配 #0…#16` **17 × 256 MiB = 4.25 GiB**（按整池容量开的 bf16 解码副本），`nvidia-smi` 18,987 vs `rk4v4` 14,557 MiB（**+4.43 GiB**），窗口封顶塌到 65,536。
- 改成"虚拟预留 + 惰性物理后备"后（引擎 commit `9392b8e`，tag `window-lazy-physical-20261014`）：
  - 分配行原文：`#16 pages=4097 heads=4 虚拟 514.0 MiB×2 已提交 8.0 MiB×2（惰性物理后备，与量化平面同页表）` ⇒ 17 层合计**已提交 ~272 MiB**；
  - 65,536 对照：`kvarn128 … runtime 2.63 GiB | free 5.35 GiB` vs `rk4v4 … runtime 2.58 GiB | free 5.42 GiB` ⇒ **差 0.05 GiB**（判据 ≤ +0.1 GiB）；
  - **262,144 起来了**：`capacity | KV 262,144 tokens, kvarn128, explicit | pages 4,096/4,096 | runtime 6.26 GiB | free 1.71 GiB` + `api base http://127.0.0.1:18141/v1`；
  - 数值未动：`PPL 5.84802 / 6.60954`（与不变量在打印精度内一致），FULL=1 回退路同值；采样峰值 18,987 → 14,901 MiB。
- **仍未闭合**：封口/未封口对拍 FAIL（`cos=0`、`|inv_rot(stage)|=0`，且 `NINFER_KVARN128_WINDOW_FULL=1` 同样 FAIL ⇒ 更像 dump/对拍脚本口径问题，未查到底）；门禁 `ctrl-rst`、`toolsctrl vs tools`、短提示词 106/51/1 **没跑**；`generation_service.cpp` 改动 ±1473 行 ⇒ **该件未经完整门禁，别当已验证件用**。

## 3. 与 llama.cpp 原生 KV 档对拍（只读源码 + CPU oracle，码流逐字节校验）

- KV 允许集合（`ref-beellama/src/common/arg.cpp:341-357` 逐行读回）：`F32,F16,BF16,Q8_0,Q4_0,Q4_1,IQ4_NL,Q5_0,Q5_1,Q6_0,Q6_1,Q3_0,Q3_1,Q2_0S,Q2_1` —— **没有 `q4_K`**（`QK_K=256` 权重档，`ggml_row_size(Q4_K,128)` assert）。
- 同字节 4.5 bpw（`real_g128`，256-dim head 口径，cos_glob）：K 侧 **KVarN 0.9980816** > `llama+rot q4_K(假想)` 0.9975130 > `llama+rot iq4_nl` 0.9969349 > `llama iq4_nl` 0.9960991 > `llama q4_0` 0.9945548；V 侧 `llama iq4_nl` 0.9961466 **> KVarN 0.9948257**。
- 杠杆排序：`q4_K 的 per-32 min+6bit 子 scale` > `Hadamard 旋转`（零字节）> `iq4_nl 非线性码本` > `KVarN 的 Sinkhorn 平衡`（K +0.00039、**V −0.00250 是净负项**）。
- 口径纠错（子代理自抓）：按 128-dim 切片量 cos 时**跨片 Hadamard 会搬能量**（不变性自检 Δcos 9.2e-4 失败）；改 256-dim head 向量后 Δcos 1.1e-10 才通过 —— 旧口径下 "V 侧 worst-token 0.85" 是切片假象（真实 0.991）。
- 校验：`iq4_nl/q3_0/q3_1` 等 9 档 numpy 独立重写与 C++ **码流 hex 逐位相同、max|Δdeq|=0**；回归：旧档原始输出逐字节相同 169/170（唯一不同的是运行日志 `dump_log.txt`）。
- **PPL 层没有一条实测**（评 llama 原生 KV 档要在 x99 另建 llama.cpp 运行面）；而本会话已实测 **"逐向量 cos 不是 PPL 的有效代理量"**（`k16` Vcos 0.9875 ≪ K4V4 的 0.9952，语料 A 的 PPL 却与后者小数点后四位相同）⇒ 上述表只能说明"千分位差异"，不能判质量优劣。

## 5. 未决项（若日后重启这条线，从这几条接着做）

1. **引擎级 ngram bug**：`--ngram-draft-tokens 0` 会触发 FATAL（`target returned a token outside the public token domain` → `exit status 2`，出现 1 次未复现）；且 ngram 混合起草写入的 KV ≠ 冷算 KV ⇒ 门禁 `ctrl/rst/rst2` 在新件上过不了（同二进制的 `rk4v4` 臂也过不了）。**这条与 KVarN 无关，是引擎自身的**，日后任何新件上生产都得先修。
2. **对拍 FAIL 未查到底**（窗口 dump 目录/口径），以及门禁全套、短提示词三档未在新件上跑。
3. `k32` 若要落地，需要**新 V 码流**（3bit 主码 + k 个通道的 4bit 支码 + 每 tile 256 bit 掩码）与 encode 侧逐 tile 通道能量排序 —— 不是"加一个位宽 case"能了事的。
4. **评测集太小**（合并 11,392 token）：要判 0.1% 级质量差，需 ≥5 万 token 级 held-out 语料。
