## 0. 结论先行

1. **细案 §2.3 的 8192/4096/640/512 是「每页总量」，不是 `leading_extent`。** ninfer 的
   `leading_extent` 是**每 token 行的元素数**（plane 形状 `{leading, 64, kv_heads, pages}`，
   `paged_kv_cache.cpp:104-107`；偏移式 `Leading*64*(head+Heads*page)+Leading*row+leading`，
   `paged_kv_address.cuh:47-61`）。按这一点算出的 P1 真值是
   **`k_code_leading=32·kb`、`v_code_leading=32·vb`、`k_scale_leading=10`、`v_scale_leading=8`**
   （K4V2 ⇒ 128 / 64 / 10 / 8；细案的 8192/4096/640/512 = 这四者 × 64 的页总量）。
   细案的**字节账没错**（K4V2 每 tile 29,184 B 与本档逐字节相同），错的只是字段单位。
2. **P1 与 gate2 整 tile record 布局逐位可互相换算，且与 oracle dump 的 record 逐段一致 —— PASS。**
   真实数据 6 档（K4V4/K4V2/K4V3/K3V3/K5V5/K6V6）× 8 个 tile：**总检查 3,293,568 项，不一致 0**。
   其中码流 3,145,728 个码元素（kb 位整值）双向搬运 0 失配，轴向 73,728 个 half 逐字节 0 失配，
   192 条 record 的 P1→record 反向重建**逐字节相等**。
3. **P1 相对 record 口径每 tile 每 head 多花 1536 B = 12 B/token/KV head**，来源可枚举导出：
   768 个**维轴**条目（K 的 scale+zp 各 2×128、V 的 other 2×128）在 tile 两页各存一份。
   P1 闭式 `32·(Kb+Vb)+36`，record 闭式 `32·(Kb+Vb)+24`，差恒为 12。
4. **K4V2 落地 228 B/token（= 生产 280 的 81.43%，省 18.57%）；K4V4 落地 292（104.29%，比 rk4v4 多 4.3%）**。
   见 §6 全表。
5. **消费核不需要知道 sibling 页 —— 不需要。** 依据：页内自足（本页 64 token 的码 + 本页 token 的列因子 +
   两 slice 的维轴副本全在该页），且引擎寻址式（`paged_kv_address.cuh:63-69`）只读
   `block_table[position>>6]`。已在 GPU 上用**引擎真头**复核 128 个位置 0 失配（§5.2）。
   需要 sibling 的是**写侧**（编码核要把维轴写进两页），见 §7。

## 3. 页内偏移表（规则 + 机器可读 CSV）

plane 元素偏移（照抄 `paged_kv_address.cuh:47-61`）：

```
offset(元素) = Leading*64*(head + Heads*physical_page) + Leading*page_offset + leading
```

`page_offset` = 页内行（0..63），`leading` = 行内列（0..Leading-1）。P1 的槽位分配：

### 3.1 码 plane（列 = 行内字节；行 = 页内 token）

- **K（上游是转置的）**：全局维 `d = slice*128 + r`（r 是 record 的 dim 行号）→ 页内位偏移 `d*kb`，
  条带 `record 字节 = r*16*kb + (T*kb)/8`（dim 行 × 128 token 的扁平位流）。
- **V（上游不转置）**：`d = slice*128 + r` → 页内位偏移 `d*vb`，条带 `record 字节 = T*16*vb + (r*vb)/8`。
- 位内一律 **LSB-first**，每行独立字节对齐（`32·bits` B/行，对 2/3/4/5/6/8-bit 都是整数，故 3/5/6-bit 不串行）。
- `row = T % 64`（T 是 tile 内 token 号 0..127），`page = T / 64`。

### 3.2 K scale plane（10 槽/行）

| 列 | 内容 | 语义 | record 来源 |
|---|---|---|---|
| 0..3 | `scale_axis` | 全局维 `d = 4·row + col`（slice = d/128, r = d%128） | 该 slice 记录 `payload + 2r` |
| 4..7 | `zp_axis` | 同上 `d = 4·row + (col-4)` | `payload + 256 + 2r` |
| 8 | `other_axis[slice 0]` | 本页 token（`T = page*64 + row`） | slice0 记录 `payload + 512 + 2T` |
| 9 | `other_axis[slice 1]` | 同上 | slice1 记录 `payload + 512 + 2T` |

### 3.3 V scale plane（8 槽/行）

| 列 | 内容 | 语义 | record 来源 |
|---|---|---|---|
| 0..3 | `other_axis` | 全局维 `d = 4·row + col` | 该 slice 记录 `payload + 512 + 2r` |
| 4 | `scale_axis[slice 0]` | 本页 token `T` | slice0 记录 `payload + 2T` |
| 5 | `scale_axis[slice 1]` | 同上 | slice1 记录 `payload + 2T` |
| 6 | `zp_axis[slice 0]` | 同上 | slice0 记录 `payload + 256 + 2T` |
| 7 | `zp_axis[slice 1]` | 同上 | slice1 记录 `payload + 256 + 2T` |

**轴向语义的依据（上游原文）**：`kvarn.cu:753-755` 写 `scale_axis[row]/zp_axis[row]/other_axis[row]`，
而 `kvarn.cu:779-786` 的 `token = value ? row : col; dim = value ? col : row;` 定死「K 转置、V 不转置」
⇒ K 的 scale/zp 是**每维**（rows=dim=128）、other 是**每 token**（cols=128）；
V 的 scale/zp 是**每 token**（rows=128）、other 是**每维**（cols=dim=128）。与 `03`/细案 §2.2 一致。

CSV `out/p1_slot_map_g128.csv` 逐槽给出（13 列）：
`tier, plane, page_row, col, slot_index_in_plane, item, slice, index, dim_d_or_token, leading_elements,
record_segment, record_byte_offset_in_record, engine_element_offset(page=0,head=0)`。
例（K4V2，K scale 第 0 行）：

```
K4V2,k_scale_pages,0,0,0,k_scale_axis,0,0,0,10,scale_off,0,0
K4V2,k_scale_pages,0,3,3,k_scale_axis,0,3,3,10,scale_off,6,3
K4V2,k_scale_pages,0,4,4,k_zp_axis,0,0,0,10,zp_off,256,4
K4V2,k_scale_pages,0,8,8,k_other_axis,0,0,-1,10,other_off,512,8
K4V2,k_scale_pages,0,9,9,k_other_axis,1,0,-1,10,other_off,512,9
```
（码 plane 的行 3,145,728 个元素由程序**逐元素**核过，故 CSV 里只按 `(slice, dim)` 给公式行 + record 行字节偏移。）

## 4. 推导链：哪些是 ninfer 硬约束、哪些是上游语义

### 4.1 ninfer 侧**硬约束**（读出来引用）

| # | 约束 | 出处 | 对 P1 的含义 |
|---|---|---|---|
| E1 | 页 = 64 token，`page_tokens != 64` 直接 `throw` | `src/core/paged_kv_cache.cpp:40-43`：`if (geometry.page_tokens != kPagedKVPageSize) throw …("requires 64-token pages")`；`kPagedKVPageSize = 64`（`src/core/paged_kv_cache.h:19`） | tile 必须拆成**恰好 2 页** |
| E2 | `leading_extent > 0 && head_extent > 0` | `paged_kv_cache.cpp:45-49` | 无上界、无 2 的幂、无字节对齐要求 |
| E3 | plane 形状 = `{leading_extent, 64, head_extent, pages}`（PageMajor） | `paged_kv_cache.cpp:104-107` | `leading` 是**每 token 行**元素数，`ne[1]` 恒 64 |
| E4 | 运行期 `require_shape` 精确相等 | `src/ops/kv_cache/append/kv_cache_append.cpp:20-25` + 调用点 `:52-55`（k/v 码）、`:75-79`（k/v scale）；attention 侧同形 `src/ops/softmax_attention/dense/causal_cache/causal_softmax_attention.cpp:111/134` | 四平面的 leading 必须与 `d256_profile.h` 里 `key/value_leading_extent`、`scale/value_scale_leading_extent` 四字段**逐字一致** |
| E5 | plane **区域**对齐 256 B | `src/core/paged_kv_cache.h:53` `std::size_t alignment = 256;` → `paged_kv_cache.cpp:107` 传给 `LayoutBuilder::add_tensor(..., plane.alignment, label)` | 只约束整个 plane 区域起点；**不**约束每 token 行宽 |
| E6 | 偏移式 | `src/ops/kernel/paged_kv_address.cuh:47-61`（本档照抄） | 见 §3 公式 |

**「leading 必须是 2 的幂 / 256 B 对齐」——不成立，有反例在引擎里已跑**：
`src/ops/kv_cache/d256_profile.h:120-121` 给 `KvarnSinkhorn4KeyInt4ValueGroup64` 的
`scale_leading_extent = 9`（**非 2 的幂**），`src/core/paged_kv_storage.h:97-98` 同值；
`d256_profile.h:131` 的 `Nvfp4Group16` 用 16、`Fp8KeyNvfp4Value` 的 key scale 用 1。
即引擎自己接受的 leading 集合里有 `1,4,8,9,16` ⇒ P1 的 `10/8`（K 轴行宽 20 B）在引擎侧合法。
（20 B 行宽不是 16 B 的倍数 ⇒ 每 4 行才回到 16 B 对齐；这只影响 load 效率，**不影响正确性**，见 §8-2。）

### 4.2 上游（beellama）语义

| # | 语义 | 出处 |
|---|---|---|
| R1 | record 布局 `rows = value?128:record_dim`、`cols = value?record_dim:128`、`payload=rows*cols*bits/8`、`scale_off=payload`、`zp_off=payload+rows*2`、`other_off=payload+2*rows*2`、`record=other_off+cols*2` | `ref-beellama/src/llama-kvarn.cpp:673-688` `llama_kvarn_make_record_layout` |
| R2 | D256 ⇒ `record_dim=128, head_slices=2`（每 tile 每 head = 2 份 K 记录 + 2 份 V 记录） | `llama-kvarn.cpp:690-698` `geometry_for` case 256 |
| R3 | 每记录字节闭式 `2048·bits + 768`（= rows=cols=128） | gate2 实测（GATE2 文档 §2.3）+ 本档 192/192 条 record 尺寸自检 |
| R4 | **K 转置、V 不转置** | `kvarn.cu:779-786`；读侧 `fattn-mma-kvarn-load.cuh:219-220` |
| R5 | 位串：连续位流、位内 LSB-first、每行 `16·bits` B 独立对齐 | `kvarn.cu:734-747`；`llama-kvarn.cpp:715-748`；读侧 `fattn-mma-kvarn-load.cuh:5-50` |
| R6 | 轴语义同 §3.2/§3.3 依据 | `kvarn.cu:753-755` + `:779-786` |

**由 R1+R2 推出的结构事实（P1 必须处理的）**：record 是「一个 slice 的 128 dim × 128 token」的
**整块**结构，没有 64-token 页的概念 ⇒ 一页只装 64 token 就只能**重新打包**（dim 行被劈开），
不存在「整块裁一半」的取法。本档的重打包是**严格双射**（§5 的 ①/③ 断言）。

检查项定义：
- **① record 尺寸/形状自检**：每条 dump 的 `rec.size()` == `make_record_layout(128,bits,value).record_bytes`
  == `2048·bits+768`，且 `rows==cols==128`、`bits` 与档位一致（192/192）；
- **① 码流逐位**：把 record 的每个码（kb/vb 位整值）搬进 P1 页槽再读回，逐元素比对
  （3,145,728 项 = 6 档×8 tile×2 平面×2 slice×128×128）；
- **③ P1→record 反向重建**：从 P1 两页反向重建整条 record 并与 oracle 原 record **逐字节**比
  （192 条 = 6 档×8 tile×2 slice×2 平面）；这条同时是**双射断言**（若映射有碰撞必失败）；
- **② 轴向逐段**：每个轴 half 从 P1 槽位读出与 record 分段字节比（73,728）；
- **④**：K scale 列 0..7 / V scale 列 0..3（维轴槽）在页 0 与页 1 逐字节一致（73,728）。

## 6. 多花字节与 B/token（结论表）

**推导（不是假设）**：程序枚举 P1 两页全部槽位做 tally，得到
「**K scale 256 + K zp 256 + V other 256 = 768 个维轴条目**，每个条目的预期槽位数 2（两页各一份）、
token 轴条目预期 1（本页一份）」全部成立 ⇒ 多花 `768 × 2 B = 1536 B/tile/head = 12 B/token/KV head`，
并与 `(P1 tile bytes − record tile bytes)` **逐档对账相等**（36/36）。

| 档 | P1 B/token | record B/token | 差 | 相对生产 `rk4v4 = 280` |
|---|---|---|---|---|
| **K4V2** | **228** | 216 | +12 | **81.43%（省 18.57%）** |
| **K4V3** | **260** | 248 | +12 | 92.86%（省 7.14%） |
| **K3V3** | **228** | 216 | +12 | 81.43%（省 18.57%） |
| **K4V4** | **292** | 280 | +12 | 104.29%（**多 4.29%**） |
| **K5V5** | **356** | 344 | +12 | 127.14% |
| **K6V6** | **420** | 408 | +12 | 150.00% |
| （K2V2，参考） | 164 | 152 | +12 | 58.57% |
| （K8V8，参考） | 548 | 536 | +12 | 195.71% |

- P1 闭式：`32·(Kb+Vb) + 36`；record 闭式：`32·(Kb+Vb) + 24`；**差恒为 12**。
- 12 的构成：K 维轴（scale+zp，2 slice×128 各一份）多 512 half = **1024 B**；V 维轴（other，2 slice×128）
  多 256 half = **512 B**。合计 1536 B。
- **与 record(280/216) 的差及原因**：record 把 `other_axis` 按 slice 各存一份（`2048·bits+768` 的 768），
  维轴在**整 tile** 只存一份；P1 为「页自足」把**维轴**在 tile 两页各存一份 ⇒ 恒定 +12 B/token。
  P1 的 228/292 与**旧 G64 路线的实测口径 228/292 逐档相等**（`oracle-结果-20261013.md` §1.3：
  146+82 / 146+146）——两者都按「每页一份侧信息」记账（每 token 每平面 9 个 half = 18 B 侧信息 ×2 平面 = 36 B/token），
  所以量级互相印证；但 K4V4 下 **P1 比 record 口径贵**（292 > 280 = 零收益）。
- 327,680 token / 4 KV head：K4V2 = 327680×228×4/1024² = **285.0 MiB**（record 口径 270.0 MiB）；K4V4 = **365.0 MiB**（record 280 → 350.0 MiB）。

## 7. sibling 页：**不需要**

- **消费核不需要 sibling 页。** 依据三条：
  1. 引擎寻址式本身只依赖 position 自己的页：`paged_kv_address.cuh:63-69`
     `paged_kv_element_offset(block_table, head, position, leading) = …(paged_kv_physical_page(
     block_table, position), head, position & kPagedKVPageMask, leading)`，无 sibling 项；
  2. P1 每页内容自足（§3 的槽位表 + §5 的 ④：维轴两页一份不差，token 轴各存本页 64 token）；
  3. GPU 真头探针（§5.2 `[sib ]`）在 128 个位置 0 失配。
- 最小寻址式（照抄引擎，二选一）：
  ```
  offset = Leading*64*(head + Heads*block_table[position>>6]) + Leading*(position&63) + leading
  # 或直接调 paged_kv_element_offset<Leading,Heads>(block_table, head, position, leading)
  ```
  同一页内两次寻址只差 `Leading*Δ(position)`，跨页即换 `block_table[position>>6]`。
- **需要 sibling 的是写侧**：编码核（A/C 封口）要把**维轴**同时写进 tile 的两页（K scale 列 0..7、
  V scale 列 0..3），所以写侧要么拿到两页句柄、要么按「tile 偶数页起始」约定算
  `sibling = even_page ^ 1`（细案 §6.2）。这属生产者约束，与消费核无关。

## 8. 未确认（不编）

1. **码 plane 的「行内重打包」对真实 kernel 的成本未测**：P1 把 K 从 record 的 dim-major 改成
   token-major（行内 256 维连续），编码/解码 kernel 的访存合并度与 bank 冲突未评估（本档只验布局正确性）。
2. **K scale 行宽 20 B（10 half）非 16 B 倍数** ⇒ 行起点每 4 行才 16 B 对齐；4-bit 之外的
   3/5/6-bit 每行内还有非字节对齐的码边界。这只影响 load 效率，正确性不受影响，但**未实测**；
   如需 16 B 对齐可把 K scale leading 抬到 16 half（代价 +12 B/token，不建议）。
3. **未跑真机编码 kernel**：本档的「与 oracle 一致」是**布局搬运**层面的逐位/逐字节一致（oracle record ↔ P1 页），
   没有重跑 `kvarn_quantize_tile`。结合 gate2 的 iters=0 576/576 逐字节 PASS，等价链条是
   「kernel 输出 == record（gate2）」+「record ↔ P1（本档）」；若要做端到端，仍需一次「编码核直写 P1 plane」的对拍。
4. **8-bit 只给了字节账**（CSV 36 档含 8），未生成 dump 对拍（`dumprec` 与 gate2 的位串分支覆盖 2/3/4/5/6）。
5. **`LayoutBuilder` 内部是否对 plane 区域有额外对齐/尺寸约束未读**（只读到 `alignment=256` 被传入
   `paged_kv_cache.cpp:107`）；若它对 region 字节数有倍数要求，plane 总字节（64×leading×elem×heads×pages）需要复核。
   P1 的页字节：K 码 2048·kb、V 码 2048·vb、K 轴 1280、V 轴 1024 —— 除 1024/1280 外的组合未见倍数关系问题，但未验。
6. **P2（维轴只存偶数页，`leading = 9344/4864`，222 B/token）未实现**：它要 sibling 寻址（细案 §2.3 备选），
   本档只做 P1。P1 相对 P2 多的 6 B/token 与「消费核不需要 sibling」是这次没做的取舍数据另一半。
7. **行号基准**：本档 `引擎` 行号来自 `engine/ninfer-all-kvarn/`（旧路线工作树，含 kvarn 文件），
   **未与 60f18c3 逐行核**；`P1` 口径的所有引用以函数名/结构名为准。
8. **`make_layout` 口径（210/274）与 P1 的关系未再核**：本档只对 record 口径（280/216，已由阶段 1 定案）做差；
   `make_layout` 在引擎里无调用者（阶段 1 已定案），未再引用。
