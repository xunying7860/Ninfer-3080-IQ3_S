## 3. 容量与最大可行窗口（可用 runtime 预留恒为 `7,553,613,824` B，三臂相同）

| 臂 | 65,536 | 131,072 | 196,608 | 262,144 | 317,440 | 最大 |
|---|---|---|---|---|---|---|
| `kvarn128` | OK `2.63 GiB / free 1.09` | FAIL | FAIL | FAIL | FAIL | **65,536** |
| `rk4v4` | OK `2.58 / 5.42` | OK `3.74 / 4.26` | OK `4.90 / 3.10` | OK `6.06 / 1.93` | FAIL | **262,144** |
| `int8` | OK `3.61 / 4.39` | OK `5.80 / 2.20` | FAIL | FAIL | FAIL | **131,072** |

**窗口塌方的直接原因（日志原文，我本地逐条数过）**：`kvarn128` 每过一个注意力层就按**整池容量**再开一份 bf16 解码窗口 ——

```
ninfer: KVarN128 窗口已分配 #0 pages=1024 heads=4 128.0 MiB×2（真解码，与量化平面同页表）
…
ninfer: KVarN128 窗口已分配 #15 … 128.0 MiB×2
ninfer: KVarN128 窗口已分配 #16 pages=1025 heads=4 128.1 MiB×2
```

首个 boot 日志里唯一编号 `#0…#16` 共 **17 份 × 256 MiB = 4.25 GiB**，对上 `nvidia-smi` 同窗口比 `rk4v4` 多的 **4.43 GiB**（18,987 vs 14,557）。窗口翻倍时每份也翻倍（`pages=2048 256.0 MiB×2`）⇒ 量化平面省下的字节被这份 bf16 全量副本吃光还倒亏，这就是**窗口封顶 65,536 的全部原因**，不是 KV 账（292 vs 280 B/token）的问题。
`131072` 起的失败原文：`startup failed | preparing CUDA graphs` → `text/layers/35 verify columns=4: kv_cache_append: KVarN128 consumer window unavailable`（分别卡在 layers/35、/15、/7）。
`317440` 三臂全败，原文：`requested Engine runtime reservation requires 7,821,150,720 / 7,562,116,608 / 12,915,488,256 bytes, but only 7,553,613,824 bytes are available` —— 注意本测试臂 flag 里带 `--vision … --media-cache-mib 512 --media-live-mib 1024`（沿用上一手骨架），比生产 `run.sh` 多约 1.5 GiB，生产口径下 `rk4v4` 是能到 317440 的（`pages 4,960/4,960 | free 253.7 MiB`），**这条差异不属于被测档位**。

## 9. 建议

1. **先修 bf16 全量窗口**（当前是"省 4bit、赔一整份 bf16"，经济账直接为负），判据见 §7 第一行。
2. 修完再谈 `tools` 套件的 KVarN 特有失败与 prefill 归因；两者都可能在窗口改造后一起消失，先别单独动量化算法。
