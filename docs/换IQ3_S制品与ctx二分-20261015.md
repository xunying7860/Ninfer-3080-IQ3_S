## 结论（一行版）

生产模型由 `Qwen3.8-27B-Coder390-EfficientThink-Q2LynnStyle-MTP.ninfer` 换成 **`gsq_rco_iq3_s_dflash2_prop.ninfer`**、
`--model-id` 改成 **`qwen3.8-27b-gsq-rco-iq3s`**、`--max-context`/`--kv-capacity` 由 317440 二分抬到硬顶 **378944**，
**其余参数一字未动**（KV 仍 `rk4v4`、投机仍 `--spec mtp --draft-tokens 3 --adaptive-mtp`、磁盘层与设备检查点照旧）。

## ctx 二分（从大往小试，`scripts/ctx-bisect.py`，逐档记录 `docs/ctx-bisect-result-20261015.txt`）

拒启是引擎的**标准输出**而不是崩溃，原文形如：

```
FATAL server failed during startup | requested Engine runtime reservation requires A bytes,
but only B bytes are available for runtime capacity
```

本次 `available runtime capacity` 恒为 **8,711,241,728 B**。

| 档位 | 结果 | 依据 |
|---|---|---|
| 393216（384K） | ✗ | requires 8,982,551,296 > available 8,711,241,728 |
| 383744 | ✗ | requires 8,802,203,392 > available 8,711,241,728 |
| 379008 | ✗ | requires 8,712,029,440 > available 8,711,241,728（**只差 768 KiB = 64 token**）|
| **378944** | **✓ 定稿** | `capacity \| KV 378,944 tokens, rk4v4, explicit \| pages 5,921/5,921 \| runtime 8.11 GiB \| free 241.7 MiB` |
| 378880 / 378816 / 378688 / 376640 / 374272 / 355328 | ✓ | 二分过程中的中间档全部通过 |

脚本做法（可复用）：改 `run.sh` 里 `--max-context \d+ --kv-capacity \d+` → `systemctl stop/start ninfer` →
在新日志片段里等 `engine ready`（成功）或 `available for runtime capacity`（失败）→ 二分收敛到 64 token 粒度 →
把最大成功值写回 `run.sh` 并起服务。每档约 20–50 s（停机走 `ExecStop` 钩子）。

**为什么能比 310K 多 68K**：`available runtime capacity` 不是常数 —— 它随**制品权重体积**变。
Q2LynnStyle 时代权重 12.3 GiB 时是 7,553,613,824 B（这正是当年「310K 是硬顶」的来源），
换 IQ3_S 后权重降到 11.3 GiB，可分配量涨到 8,711,241,728 B（+约 1 GiB）。

## ⚠️ 附带发现：GPU 级偶发异常 Xid 13（**与本次换模型 / 抬 ctx 无因果**）

196K 第 1 次 prefill 跑到 15:22:46 时：

```
NVRM: Xid (PCI:0000:03:00): 13, Graphics SM Warp Exception on (GPC 3, TPC 3, SM 0): Misaligned Address
NVRM: Xid (PCI:0000:03:00): 13, Graphics SM Global Exception on (GPC 3, TPC 3, SM 0): Multiple Warp Errors
NVRM: Xid (PCI:0000:03:00): 43, pid=<引擎>
```

引擎侧只报了**下游现象**：`./src/core/device.cu:402 CUDA_CHECK(cudaStreamSynchronize(...)) failed: cudaErrorMisalignedAddress`，
进程 `status=6/ABRT`，systemd 15 s 后自动拉起（`NRestarts=1`）。

**三条反证 ⇒ 不能归因给这次改动**：

1. 同日 12:10:32 同一张卡（GPU0 / PCI `03:00`）已报过同族 Xid 13（`Illegal Instruction Encoding`），
   当时跑的是**旧模型 + 旧 ctx 317440**。
2. 同一 196K 负载第二次**通过**（非确定性，不像软件必现缺陷）。
3. 两次 Xid 都落在 `GPC 3, TPC 3, SM 0`（ESR 不同）⇒ 更像硬件侧该 SM 不稳。

基线登记（供后续对比）：`dmesg -T | grep Xid`、`systemctl show ninfer -p NRestarts --value`、
日志里 `device.cu:402` / `status=6/ABRT`。未经证实的怀疑对象：`gpu-clocks.service` 的降压超频
（`--gpc-offset 250 --mem-offset 500 --gclock-max 1800 --watts 320`，两卡同设）。
现成定点工具 `/data/workspace/qwen38_sglang/bin/gpu_stress.py`（两卡 GEMM 拉满 + 数值校验 + Xid 判定），
**尚未跑**（会与常驻引擎抢显存，需先停引擎）。
